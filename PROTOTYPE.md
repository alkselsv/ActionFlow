# Прототип ActionFlow

Обновлено: 2026-11-19 по итогам согласования первого эксперимента.

Согласованные требования, критерии проверки и открытые решения находятся в [спецификации MVP](docs/specs/responseflow-mvp.md). Порядок работ, зависимости и критерии будущих тикетов — в [дорожной карте](docs/ROADMAP.md). Этот документ описывает архитектуру прототипа. Термины определены в [GLOSSARY.md](GLOSSARY.md).

## Цель прототипа

ActionFlow — самостоятельный продукт. **ResponseFlow** — его первый модуль для мониторинга клиентских коммуникаций Vedita. Прототип проверяет этот сценарий и становится основой развития продукта.

Прототип не должен воспроизводить всю будущую платформу. Его задача — проверить ключевые продуктовые гипотезы:

1. Можно ли стабильно получать и нормализовать клиентские сообщения?
2. Насколько точно система выявляет вопросы без ответа, обязательства, претензии и другие значимые ситуации?
3. Понятны ли менеджеру приоритет, evidence и рекомендуемое действие?
4. Сокращает ли единая очередь ситуаций время реакции?
5. Какие действия можно безопасно автоматизировать?

## Границы первой версии

Первая версия анализирует текст экспортированных групповых чатов Telegram и показывает findings одному менеджеру Vedita в веб-интерфейсе. Один чат соответствует одному проекту; у клиента может быть несколько проектов. В чате находятся представители Vedita и клиента.

При импорте вручную задаются клиент, проект, стороны участников и ответственный менеджер. Неустановленная принадлежность участника обозначается как неизвестная. Контекст проекта и SLA также задаются вручную. SLA зависит от типа клиента; значения, рабочие часы и часовой пояс настраиваются для проекта.

Анализ запускается кнопкой после импорта. Для первого эксперимента достаточно одной учётной записи с доступом ко всем его проектам.

В прототип входят:

- импорт исторической переписки;
- нормализация и хранение сообщений;
- ручная настройка проектного контекста и SLA с сохранением версий;
- обнаружение значимых ситуаций;
- определение приоритета;
- краткое описание и рекомендация;
- ссылки на сообщения-основания;
- дедупликация;
- очередь менеджера;
- подтверждение, отклонение, откладывание и закрытие finding;
- сбор feedback;
- replay, сравнение запусков и измерение качества детекторов.

В первую версию не входят:

- Telegram-бот, постоянная синхронизация и уведомления;
- анализ содержимого вложений и голосовых сообщений;
- загрузка проектной документации и извлечение SLA из проекта;
- несколько пользователей и разграничение доступа между ними;
- автоматическая отправка сообщений клиенту;
- создание значимых задач без approval;
- одновременная поддержка всех каналов;
- универсальный конструктор workflow;
- сложная multi-agent оркестрация;
- собственный аналог Temporal;
- обязательное использование knowledge graph: роль Cognee проверяется экспериментом;
- прогнозирование оттока без накопленных данных.

## Минимальная архитектура

```text
Telegram JSON export
          ↓
  Message ingestion
          ↓
 PostgreSQL + ручной контекст и SLA
          ↓
 Кнопка «Анализировать»
          ↓
 Temporal → Python Worker
          ↓
 ResponseFlow Detector
    ├── правила
    └── LLM-анализ
          ↓
 Finding + Evidence
          ↓
   Очередь менеджера
    ├── подтвердить
    ├── отклонить
    ├── отложить
    └── закрыть
          ↓
 История решений и сравнение запусков
```

### Компоненты

| Компонент | Ответственность |
|---|---|
| Import/Connector | Импорт экспорта; далее получение сообщений ботом |
| Message Store | Хранение сообщений и ревизий |
| Context Provider | Ручной контекст и SLA; далее документация и поиск через Cognee |
| Detectors | Обнаружение значимых ситуаций |
| Finding Service | Дедупликация и жизненный цикл ситуации |
| Commitment Tracking | Содержание обещаний, исполнитель, сроки и основания изменений |
| Priority Policy | Расчёт срочности |
| Manager Inbox | Очередь ситуаций |
| Temporal | Выполнение анализа; далее расписания, сроки и ожидания подтверждений |
| Notification Adapter (следующий этап) | Уведомления в Telegram или Битрикс24 |
| Feedback Store | Решения менеджера и данные для evaluations |

## Рекомендуемый стек

Рабочий стек самостоятельного приложения:

- Python 3.14.10;
- FastAPI;
- Pydantic;
- SQLAlchemy и Alembic;
- PostgreSQL;
- LiteLLM или собственный минимальный интерфейс LLM-провайдера;
- Instructor либо native structured output модели;
- Temporal Server и Python SDK для фоновых процессов, дальнейших расписаний и ожиданий;
- React + TypeScript + Vite для очереди менеджера;
- Docker Compose для локального запуска;
- pytest для детекторов, контрактов и replay-тестов.

Версии зафиксированы 2026-11-21 в [af-004-stack.md](docs/experiment/af-004-stack.md): FastAPI 0.165.0, Pydantic 2.14.4, SQLAlchemy 2.1.9 (синхронный доступ), Alembic 1.20.1, PostgreSQL 16.16, Temporal Server 1.32.2 и Python SDK 1.36.1, Node.js 26.13.1 LTS, React 19.3.1, TypeScript 7.0.2, Vite 8.3.8. Совместимость проверена минимальными запусками; приложение ещё не реализовано.

Temporal заменяет предложенные ранее APScheduler и Celery для этих процессов. Redis для расписаний и очереди Temporal не требуется. Прикладная БД и хранилища Temporal разделяются; для пилота возможен один экземпляр PostgreSQL с отдельными базами и пользователями.

Предметная логика отделяется от workflow. Работа с LLM, Cognee, БД и внешними системами выполняется в Activities; workflow задаёт порядок шагов и ожидания. Декомпозиция процессов, Activities и outbox зафиксированы в [контрактах](docs/specs/responseflow-contracts.md); эксплуатация, диагностика и восстановление — в [AF-021](docs/experiment/af-021-operations.md).

Для первого эксперимента достаточно истории переписки и ручного контекста. На M0 реальных клиентских переписок Vedita нет, поэтому первый набор — синтетический; состав и ограничения зафиксированы в [записи AF-001](docs/experiment/af-001-source-data.md). Через `ContextProvider` сравниваем базовый вариант с Cognee на одном историческом наборе. Выбор Cognee и LLM ещё не утверждён; внешние LLM/embedding-провайдеры на M0 не разрешены ([политика окружения](docs/experiment/af-004-environment-policy.md)). Сообщения, подтверждённые состояния обязательств и решения менеджера остаются в PostgreSQL. См. [исследование Cognee](docs/research/cognee-memory.md) и [примеры чатов](docs/research/cognee-chat-examples.md).

## Стратегия разработки

### Сначала исторические данные

Первый эксперимент лучше провести без подключения к живым чатам:

1. Использовать согласованный синтетический набор Telegram-style: реальных клиентских чатов Vedita нет. Если появятся реальные данные, их нужно обезличить и хранить вне Git; 10–30 чатов — первоначальный ориентир, объём ещё не согласован.
2. Вручную отметить значимые ситуации.
3. Сохранить точные сообщения-основания.
4. Зафиксировать правильный тип и приоритет.
5. Отметить сообщения, которые не должны создавать finding.

Такой набор станет первым evaluation dataset и позволит быстро сравнивать prompts, модели, правила и пороги.

### Затем живой пилот

После достижения приемлемого качества на истории подключается Telegram-бот к выбранным групповым чатам. Проверяются права доступа, полнота синхронизации, сопоставление с импортированной историей, редакции и восстановление после сбоев. Плановые запуски выполняются через Temporal Schedules, ожидания сроков — через timers внутри workflow.

На следующем этапе контекст и SLA получаем из данных проекта и документации с сохранением источников и версий. Уведомления, MAX и Битрикс24 подключаются после стабилизации основного цикла.

## Минимальная модель сообщения

```python
class Message:
    id: str
    workspace_id: str
    conversation_id: str
    sender_id: str
    sender_role: str
    sent_at: datetime
    text: str
    reply_to_id: str | None
    source: str
    external_id: str
    revision: int
```

Следует сохранять внешний идентификатор чата и сообщения, доступные редакции и время наблюдения. Экспорт не считается источником полной истории редакций и удалений. При переходе к боту соответствие идентификаторов проверяется до объединения данных. Схема выше — исходный эскиз; актуальные сущности и состояния зафиксированы в [предметной модели](docs/specs/responseflow-domain-model.md), контракты хранения — в [контрактах](docs/specs/responseflow-contracts.md).

Наличие вложений и голосовых отмечается, но их содержимое в первой версии не анализируется. Если возможный ответ находится в таком содержимом, вывод отражает неполноту данных.

## Основной capability

Рабочий эскиз контракта:

```text
detect_customer_situations(
    conversation_window,
    project_context,
    analysis_time
) -> FindingCandidate[]
```

Предлагаемый результат:

```python
class FindingCandidate:
    type: str
    severity: str
    confidence: float
    summary: str
    recommended_action: str
    evidence_message_ids: list[str]
    due_at: datetime | None
    responsible_role: str | None
    subject_key: str
```

LLM должна возвращать только структурированный результат, прошедший проверку Pydantic. Итоговый `deduplication_key` должно собирать приложение из нормализованных полей, а не генерировать модель.

## Детекторы первой версии

Начальный набор типов:

- `unanswered` — вопрос или обращение клиента без содержательного ответа Vedita;
- `commitment` — обязательство сотрудника Vedita перед клиентом;
- `complaint` — претензия клиента, требующая внимания менеджера.

Запросы документов входят в обращения. Просрочка и нарушение SLA отражаются в свойствах и приоритете ситуации. Самостоятельные детекторы `document_request`, `delay`, `sla_risk` и `manager_attention` отложены.

В первой версии один анализатор может возвращать несколько типов findings. При этом criteria, prompt version и метрики качества должны храниться отдельно по каждому типу.

## Гибридный анализ

Рекомендуется совместить правила и LLM:

1. Код проверяет формальные признаки: время последнего ответа, наличие ответа сотрудника, SLA и известные сроки.
2. LLM определяет смысл сообщения, тип ситуации и необходимость реакции.
3. Код проверяет структуру результата, дедуплицирует finding и применяет priority policy.

Например, продолжительность отсутствия ответа вычисляется детерминированно, а вывод о том, действительно ли сообщение содержит вопрос, делает модель.

### Первая реакция и решение обращения

Подтверждение получения сотрудником Vedita завершает отсчёт SLA первой реакции. Обращение остаётся открытым до содержательного ответа или предоставления результата. Сообщение представителя клиента не засчитывается автоматически как реакция Vedita.

«Принял, уточню и вернусь завтра» фиксирует первую реакцию и связанное обязательство. Содержание обещания, исполнитель и история сроков учитываются отдельно от карточки ситуации. Обязательство продолжает отслеживаться после выхода исходного сообщения из текущего окна анализа. Правила для обещаний без срока утверждены в [AF-002](docs/experiment/af-002-annotation.md). Отдельный норматив решения обращения отложен.

## Жизненный цикл finding

Менеджер может подтвердить находку, отклонить, отложить или закрыть ситуацию. Система предлагает закрытие или переоткрытие с основаниями, решение принимает менеджер. Статусы и допустимые переходы описаны в [предметной модели](docs/specs/responseflow-domain-model.md#карточка-и-действия-менеджера).

Для finding необходимо хранить:

- тип и статус;
- приоритет;
- confidence;
- краткое описание;
- рекомендуемое действие;
- evidence;
- версию детектора и prompt;
- `deduplication_key`;
- время первого и последнего обнаружения;
- решения и комментарии пользователя;
- историю переоткрытий.

Повторный анализ не должен создавать новую карточку одной и той же ситуации.

Каждый запуск сохраняет момент оценки, входной срез сообщений, версии контекста и SLA, детектора, prompt, схемы и модели, результаты, ошибки, длительность и стоимость. Кандидаты детектора сохраняются отдельно от решений менеджера. Повторные запуски доступны для сравнения с сохранением истории решений.

Три детектора выполняются последовательно как отдельные Activities. Результат каждого этапа и его метаданные фиксируются одной транзакцией с кандидатами. Подтверждённый в базе этап пропускается при повторной доставке Activity. При сбое workflow сохраняет ошибку запуска, а завершённые этапы остаются доступны. Сравнение читает сохранённые срезы и результаты без записи в очередь.

При исторической оценке исключаются сведения, ставшие доступными позже момента оценки. Replay детектора для evaluations является отдельной процедурой от replay workflow Temporal.

## Очередь менеджера

Интерфейс должен показывать очередь действий, а не просто список сообщений.

Пример карточки:

```text
[Высокий приоритет] Клиент ожидает исправленную смету

Проект: ...
Обнаружено: 2 часа назад
Основание: 3 сообщения
Рекомендация: назначить ответственного и сообщить срок

[Подтвердить] [Отклонить] [Отложить] [Закрыть]
```

Обязательные элементы:

- клиент и проект;
- приоритет;
- сообщения-основания;
- объяснение приоритета;
- рекомендуемое действие;
- confidence;
- версия детектора;
- история решений.

Очередь фильтруется по проекту, типу, приоритету и статусу. Счётчики показывают открытые ситуации и нарушения SLA на момент выбранного анализа. Полноценные аналитические дашборды отложены.

## Принципы развития ActionFlow

При развитии продукта:

- использовать стабильные capability-контракты;
- не связывать workflow с конкретным LLM или agent framework;
- хранить source identity и revisions;
- отделять `Finding` от `Evidence`;
- сохранять версии detector, prompt и schemas;
- добавлять `workspace_id` и `environment` в tenant-owned данные;
- выполнять внешние действия через `ActionExecutor`;
- обеспечивать идемпотентность connector и actions;
- собирать решения пользователя как feedback;
- проверять детекторы через replay/backtest;
- не создавать собственный долгоживущий orchestration layer.

Распределение ответственности:

- ActionFlow отвечает за предметную модель, коннекторы, детекторы, контекст проекта, правила, подтверждения, действия, права, аудит, evaluations и интерфейс;
- Temporal обеспечивает выполнение процессов, расписания, таймеры и ожидания событий;
- PostgreSQL хранит предметные данные, основания и историю решений;
- Cognee проверяется как заменяемый слой поиска контекста;
- ResponseFlow является первым модулем ActionFlow.

Отдельное платформенное ядро и перенос в другую собственную платформу не входят в план. Повторно используемые модули выделяются по подтверждённой потребности.

## Базовый workflow

Для первого эксперимента:

```text
импорт экспорта → проверка проекта, участников, контекста и SLA
  → кнопка анализа → выполнение в Temporal
  → правила и LLM → валидация оснований и дедупликация
  → приоритет → веб-очередь
  → решение менеджера → история feedback
```

Целевой workflow следующих этапов:

```text
новое сообщение или плановый запуск
  → получение и сохранение revision
  → нормализация
  → связь с клиентом и проектом
  → сбор разрешённого контекста
  → запуск детекторов
  → валидация результата
  → дедупликация / обновление finding
  → определение приоритета
  → рекомендация следующего действия
  → очередь менеджера / уведомление
  → решение человека или policy gate
  → контролируемое действие
  → проверка результата
  → закрытие finding
```

Внешняя система остаётся источником истины для собственных объектов. Например, статус задачи принадлежит Битрикс24; прототип хранит локальную проекцию, историю наблюдений и результат автоматизации.

## Этапы реализации

Детальный план ведётся в [docs/ROADMAP.md](docs/ROADMAP.md), чтобы зависимости и критерии задач имели один источник.

| Этап | Результат |
| --- | --- |
| M0 | Образцы экспорта, правила, модель данных и конфигурация эксперимента |
| M1 | Офлайн-MVP: импорт, анализ кнопкой, очередь и решения менеджера |
| M2 | Проверка качества, выбор модели и решение по Cognee |
| M3 | Telegram-бот, новые сообщения и контроль сроков |
| M4 | Документация и SLA из проектных данных |
| M5 | Уведомления и действия после подтверждения |

Измерение качества начинается в M0–M1. M2 сравнивает и улучшает конфигурации на подготовленном наборе. Условия перехода, возможная параллельность и открытые решения описаны в дорожной карте; календарные сроки пока не назначены.

## Метрики

Минимальный набор:

- precision и recall по каждому типу finding;
- false-positive rate;
- доля findings без корректного evidence;
- time-to-detect;
- время от finding до реакции;
- процент подтверждённых рекомендаций;
- количество дубликатов;
- доля ситуаций, доведённых до закрытия;
- корректность расчёта SLA первой реакции;
- объём ручной корректировки;
- стоимость обработки одного диалога или finding.

## Критерий готовности

Проверяемые функциональные критерии первого эксперимента перечислены в [спецификации MVP](docs/specs/responseflow-mvp.md#проверка-готовности). Числовые пороги качества согласуются после базового измерения; календарные сроки ещё не установлены.

Прототип можно считать успешным, если он:

- находит большую часть действительно важных ситуаций;
- не перегружает менеджера ложными уведомлениями;
- показывает точные сообщения-основания;
- объясняет приоритет;
- не создаёт дубликатов;
- сокращает время поиска проблемных коммуникаций;
- собирает feedback для улучшения детекторов;
- сохраняет контракты, данные и основания, пригодные для дальнейшего развития ActionFlow.

Главный принцип: проверить узкий ResponseFlow на качественном evaluation dataset и в работе менеджера, затем развивать ActionFlow по результатам эксперимента.
