# Синтетические Telegram-style fixtures

Эти файлы получены из предоставленного пользователем синтетического набора нормализованных JSONL-сообщений. Они предназначены для разработки и проверки последующей нормализации; это не экспорт Telegram и не реальные клиентские переписки.

Статус: согласованный входной набор AF-001 для первого эксперимента ([issue #1](https://github.com/alkselsv/ActionFlow/issues/1)). Реальных клиентских чатов Vedita нет, поэтому эксперимент выполняется на этом наборе. Состав, соответствие «чат — проект», стороны участников и правила работы с данными: [docs/experiment/af-001-source-data.md](../../../docs/experiment/af-001-source-data.md). Описание формата и ожидаемой нормализации: [docs/experiment/af-001-import-format.md](../../../docs/experiment/af-001-import-format.md).

## Проверочные примеры формата

Дополнительно к набору эксперимента добавлены 6 синтетических файлов для проверки краевых случаев импорта. Они не входят в согласованный набор из 9 чатов и не имеют привязки к клиенту или проекту:

- `edge-format-s-002.json` — 3 сообщения: составной текст с форматированием и ссылкой, неизвестный участник, ответы;
- `edge-media-s-003.json` — 6: фото, голосовое, файл, видео, стикер, подписи;
- `edge-service-s-004.json` — 5: системные события входа, приглашения, смены названия и выхода;
- `edge-edited-s-005.json` — 3: наблюдённая редакция и пересылка;
- `edge-reimport-s-006-first.json` — 3: первая загрузка;
- `edge-reimport-s-006-second.json` — 4: повторная загрузка с изменением и новым сообщением.

Итого в каталоге: 15 файлов, 14 разговоров, 67 записей. Формат, предположения и ожидаемая нормализация описаны в [docs/experiment/af-001-import-format.md](../../../docs/experiment/af-001-import-format.md).

## Перенос полей

| Исходное поле | Telegram-style поле |
| --- | --- |
| `conversation_id` | имя чата и `_actionflow_fixture.conversation_id` |
| `external_id` | `_actionflow_synthetic_source.external_id` |
| `sent_at` | `date`, `date_unixtime` и исходное значение в `_actionflow_synthetic_source.sent_at` |
| `sender_id`, `sender_role` | синтетические `from`, `from_id`; исходная роль — в `_actionflow_synthetic_source.sender_role` |
| `text` | `text` |
| `reply_to_external_id` | локальный `reply_to_message_id` и исходная ссылка в metadata |
| `revision`, `observed_at`, `source` | `_actionflow_synthetic_source` |
| `workspace_id` | `_actionflow_fixture.workspace_id` |

`date` сериализован как UTC-время, а исходное время с offset сохранено в metadata. Номера `id` в чате и `reply_to_message_id` локальны для каждого файла; исходные внешние ID не изменяются.

## Проверка

Файлы хранятся в UTF-8 без BOM, чтобы строгие JSON-парсеры принимали их без `utf-8-sig`. Проверка целостности:

```text
python scripts/validate_fixtures.py
```

Скрипт проверяет разбор JSON, пометку синтетического набора, уникальность `id`/`external_id`, порядок сообщений, согласованность времени и редакций, разрешимость ссылок ответов, роли, типы сообщений и вложений, повторную загрузку и отсутствие контактных данных. Ожидаемый вывод:

```text
OK: 15 files, 14 conversations, 67 message records, 1 re-import pair(s)
```

## Ограничения

- Входной файл уже нормализован и не содержит исходных байтов/структуры Telegram Desktop export. Эти fixtures не подтверждают реальные поля, системные типы событий, вложения, часовой пояс экспорта или поведение Telegram при редактировании/удалении.
- Проверочные примеры `edge-*` используют выбранную форму полей (`text` массивом, `type: "service"`, `media_type`, `edited`). Это проверяемые предположения о входе, а не подтверждённая схема Telegram. Неизвестные реальные поля импортёр должен сохранять без интерпретации.
- Системные записи в наборе эксперимента представлены как synthetic messages; их нельзя считать точным воспроизведением схемы Telegram service events.
- В исходнике есть даты и содержательные сценарии, но нет подтверждения, что они соответствуют выбранным клиенту, проекту, чату и периоду эксперимента. Поэтому их нельзя использовать как доказательство согласованного набора реальных данных.
- В репозитории допустимы только синтетические/обезличенные примеры. Реальные переписки и исходные экспорты следует хранить согласованно вне Git.
