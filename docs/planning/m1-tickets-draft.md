## Предпосылки и границы

- Продуктовые правила, модель, версии и технические контракты берутся из завершённых задач M0. Тикеты M1 не подменяют эти решения предположениями.
- Первая работа блокируется [#7 — контрактами и исполнением анализа](https://github.com/alkselsv/ActionFlow/issues/7). Её зависимости охватывают проверку экспорта, правила, предметную модель и стартовую конфигурацию; повторять все транзитивные блокировки в каждом тикете не требуется.
- После завершения M0 формулировки сверяются с его результатами. Если изменился согласованный объём, обновляются спецификация, план и затронутые Issues до зависимой реализации.
- Каждый тикет включает необходимое хранение, серверное поведение, отображение и проверку своего результата. Отдельные задачи на слой API или UI не выделяются.
- Промежуточные результаты явно ограничены своей возможностью: подготовленный срез не объявляется завершённым LLM-анализом, первый детектор не выдаётся за весь MVP.
- Тесты проверяют пользовательское поведение и важные сценарии восстановления; реальные переписки и секреты остаются вне Git.
- Бот, документы, уведомления, внешние действия и внедрение Cognee остаются за пределами M1. Используется базовый ручной контекст проекта.

## M1-01. Дать менеджеру вход в приложение и сохраняемый проект

**AF-ID:** AF-005, AF-006, AF-008 часть 1. **GitHub:** [#8](https://github.com/alkselsv/ActionFlow/issues/8). **Blocked by:** [#7](https://github.com/alkselsv/ActionFlow/issues/7).

**Что построить:** менеджер запускает приложение, входит, создаёт клиента и проект и видит их после перезапуска. Это первый сквозной результат через интерфейс, backend и PostgreSQL.

**Критерии приёмки:**

- [ ] Чистое окружение поднимается по инструкции с согласованными версиями; начальные миграции применяются, один документированный запуск проверок проходит.
- [ ] Единственная учётная запись позволяет войти и выйти. Неавторизованные запросы к данным отклоняет backend; секреты отсутствуют в репозитории.
- [ ] Менеджер создаёт клиента, проект и ответственного по модели M0; сохранённые данные доступны после перезапуска. Один клиент может иметь несколько проектов.
- [ ] Интерфейс показывает загрузку, пустое состояние и ошибку; проверен полный путь вход → создание → повторное открытие проекта.

**Исключения:** дополнительные пользователи, полный контекст/SLA, импорт, Temporal и LLM-анализ.

## M1-02. Настроить участников, ручной контекст и SLA проекта

**AF-ID:** AF-008 часть 2. **GitHub:** [#9](https://github.com/alkselsv/ActionFlow/issues/9). **Blocked by:** [#8](https://github.com/alkselsv/ActionFlow/issues/8).

**Что построить:** менеджер задаёт условия анализа проекта и принадлежность участников; приложение сохраняет версии этих условий.

**Критерии приёмки:**

- [ ] Доступны описание проекта, важные договорённости, ответственный, стороны Vedita/клиент/неизвестно, срок первой реакции, рабочий календарь и часовой пояс.
- [ ] Способ задания участников до и после импорта соответствует модели M0; после импорта неизвестная принадлежность может быть уточнена. Сопоставление выполняется по устойчивым идентификаторам, а не только имени.
- [ ] Условия отражают тип клиента, числовые значения берутся из согласованных настроек. Невалидный календарь или часовой пояс отклоняется с понятной ошибкой.
- [ ] Изменение сохраняет новую версию; предыдущая доступна для ссылки из исторического запуска. Данные разных проектов разделены.

**Исключения:** извлечение настроек из документов и автоматическое определение стороны участника по имени.

## M1-03. Импортировать Telegram JSON и показать переписку проекта

**AF-ID:** AF-009 часть 1, AF-010 часть 1. **GitHub:** [#10](https://github.com/alkselsv/ActionFlow/issues/10). **Blocked by:** [#9](https://github.com/alkselsv/ActionFlow/issues/9).

**Что построить:** менеджер выбирает проект, загружает поддерживаемый экспорт и читает сохранённый текст в браузере с отчётом импорта.

**Критерии приёмки:**

- [ ] Telegram JSON из примеров M0 нормализуется с внешними ID, автором, временем, составным текстом, доступной связью ответа и временем получения системой.
- [ ] Чат привязан к одному проекту; попытка противоречивой привязки обрабатывается по контракту M0. Импорт фиксирует известных и неизвестных участников.
- [ ] Видны устойчивый порядок сообщений, сторона автора, время и текст. Открытие сообщения показывает окружающую переписку; разные проекты не смешиваются.
- [ ] Отчёт показывает импортированные и пропущенные элементы. Повреждённый файл и неподдерживаемый формат дают явную ошибку; частичный результат обрабатывается по согласованному контракту.

**Исключения:** бот, анализ содержимого вложений и полный набор сценариев повторного импорта, который добавляется следующим тикетом.

## M1-04. Сохранить идентичность, редакции и ограничения при повторном импорте

**AF-ID:** AF-009 часть 2, AF-010 часть 2. **GitHub:** [#11](https://github.com/alkselsv/ActionFlow/issues/11). **Blocked by:** [#10](https://github.com/alkselsv/ActionFlow/issues/10).

**Что построить:** менеджер повторно загружает экспорт, видит изменения и ограничения источника, не получая дубликаты сообщений и ложную полноту истории.

**Критерии приёмки:**

- [ ] Повтор того же файла не увеличивает число канонических сообщений. Пересекающиеся экспорты и изменённый текст с тем же внешним ID обрабатываются по модели M0.
- [ ] Наблюдаемые редакции и связи ответов сохраняются; прежняя редакция остаётся адресуемой для основания и исторического среза.
- [ ] Вложение, голосовое, системное событие и пустой текст отражаются по правилам M0. Содержимое файлов не анализируется, наличие необработанного материала видно менеджеру.
- [ ] Отсутствие сообщения в новом экспорте не выдаётся за доказанное удаление, если формат этого не подтверждает. Доступные и неизвестные временные сведения различаются.
- [ ] Проверены повторная загрузка, пересечение, наблюдаемое изменение и повтор запроса после сбоя; история и идентичность сохраняются.

**Исключения:** восстановление ненаблюдаемых редакций и сбор удалений через живой API.

## M1-05. Подготовить исторический срез через Temporal с видимым результатом

**AF-ID:** AF-007, AF-011 часть 1, AF-018 часть 1. **GitHub:** [#12](https://github.com/alkselsv/ActionFlow/issues/12). **Blocked by:** [#11](https://github.com/alkselsv/ActionFlow/issues/11).

**Что построить:** менеджер выбирает период и момент оценки, запускает подготовку, отслеживает её и видит состав и ограничения сохранённого входа анализа.

**Критерии приёмки:**

- [ ] HTTP-запрос возвращает идентификатор; работа выполняется worker через Temporal и переживает его перезапуск. Состояние подготовки и ошибка доступны в интерфейсе.
- [ ] Вход фиксирует сообщения/доступные редакции, момент оценки, версии контекста и SLA. Поздние ответы, будущие переносы и новые настройки исключены в пределах сведений источника.
- [ ] При превышении допустимого объёма поведение явно соответствует контракту M0. Часть истории не отбрасывается незаметно; менеджер видит ограничения подготовленного среза.
- [ ] Проверены повторная доставка команды, намеренный новый запуск, ограниченные повторы, таймаут и постоянная ошибка. Сбой между записью запроса и стартом workflow восстанавливается согласованным механизмом.
- [ ] Подготовленный вход можно повторно получить по идентификатору. Интерфейс явно различает подготовку и выполненный семантический анализ; LLM ещё не вызывается.

**Исключения:** периодические расписания, живые события, внедрение Cognee и выполнение детекторов.

## M1-06. Найти обращения без ответа и показать первую карточку с основаниями

**AF-ID:** AF-012, AF-013, AF-017 часть 1, AF-018 часть 2, AF-019 часть 1. **GitHub:** [#13](https://github.com/alkselsv/ActionFlow/issues/13). **Blocked by:** [#12](https://github.com/alkselsv/ActionFlow/issues/12).

**Что построить:** кнопка анализа запускает стартовую LLM на зафиксированном входе; менеджер получает сохранённую карточку `unanswered` и проверяет её по исходной переписке.

**Критерии приёмки:**

- [ ] Стартовая модель вызывается через заменяемый адаптер в Activity. Ответ проходит проверку схемы; каждое основание существует, принадлежит проекту и доступной редакции входного среза.
- [ ] Различаются вопрос без ответа, первая реакция без решения, содержательный ответ, ответ клиента и несколько вопросов. Возможный ответ во вложении отражает неполноту данных.
- [ ] Сохраняются кандидат, карточка, основания и история обнаружений. Повторная доставка и повтор Activities не создают дубликаты; намеренный новый запуск имеет отдельный результат.
- [ ] В карточке доступны описание, рекомендация, основания и окружающая переписка; отдельное представление результата запуска показывает, что на этом шаге реализован `unanswered`.
- [ ] Проверены невалидный ответ, чужое основание, лимит провайдера, таймаут и постоянная ошибка. Версии prompt, схемы, модели, параметры, длительность, потребление и доступная стоимость сохранены; неизвестная стоимость обозначена явно.

**Исключения:** детекторы обязательств и претензий, завершённая политика приоритета и SLA, полный интерфейс решений менеджера. Уверенность модели не объявляется измеренной вероятностью правильности.

## M1-07. Рассчитать SLA и показать объяснимый приоритет в очереди

**AF-ID:** AF-016, AF-019 часть 2. **GitHub:** [#14](https://github.com/alkselsv/ActionFlow/issues/14). **Blocked by:** [#13](https://github.com/alkselsv/ActionFlow/issues/13).

**Что построить:** менеджер видит срок первой реакции, его состояние и объяснение приоритета, рассчитанные кодом по действовавшим условиям проекта.

**Критерии приёмки:**

- [ ] Расчёт использует версию SLA и рабочий календарь выбранного анализа. Проверены границы дня, нерабочее время и часовой пояс на примерах M0.
- [ ] Подтверждение получения сотрудником Vedita останавливает SLA первой реакции, но не закрывает обращение. Ответ клиента и неопределённая сторона обрабатываются по согласованным правилам.
- [ ] Политика приоритета работает с контрактами всех трёх типов; отдельные правила проверяются на согласованных кандидатах, даже если ещё не все детекторы реализованы.
- [ ] Очередь и карточка показывают приоритет, объяснение, SLA и ограничения расчёта; фильтры и счётчики соответствуют моменту анализа и версии правил.
- [ ] Недостаток данных не превращается в уверенное нарушение; изменение текущей настройки не меняет прежний расчёт задним числом.

**Исключения:** новый несогласованный норматив решения обращения и живые таймеры эскалации.

## M1-08. Отслеживать обязательства Vedita и изменения договорённостей

**AF-ID:** AF-014, AF-011 часть 2, AF-017 часть 2. **GitHub:** [#15](https://github.com/alkselsv/ActionFlow/issues/15). **Blocked by:** [#14](https://github.com/alkselsv/ActionFlow/issues/14).

**Что построить:** в анализ добавляются обязательства Vedita; менеджер видит, что обещано, кем, когда и на основании каких изменений срока или исполнения.

**Критерии приёмки:**

- [ ] Детектор и сохранение различают обещание, предположение, цитату, перенос, отмену и исполнение. Неустановленные исполнитель и срок остаются неизвестными по правилам M0.
- [ ] Обязательство имеет собственную историю и связано с карточкой через основания. Повторное обнаружение не создаёт новое обязательство для прежнего обещания.
- [ ] Повторный анализ учитывает незавершённое обязательство после выхода его сообщения из выбранного окна; будущие изменения не проникают в более раннюю оценку.
- [ ] Карточка и окружение источников показывают исходное обещание и основания изменений. Просрочка и приоритет рассчитаны по согласованным правилам.
- [ ] Сценарий обещание → перенос → сообщение об исполнении проверен на исторических срезах; предложение о разрешении не закрывает карточку автоматически.

**Исключения:** автоматическая постановка задач, уведомления и догадки об отсутствующем сроке.

## M1-09. Добавить претензии клиента в общую очередь

**AF-ID:** AF-015. **GitHub:** [#16](https://github.com/alkselsv/ActionFlow/issues/16). **Blocked by:** [#14](https://github.com/alkselsv/ActionFlow/issues/14).

**Что построить:** анализ выявляет `complaint`, а менеджер рассматривает претензию через общую очередь и исходные сообщения.

**Критерии приёмки:**

- [ ] На разметке различаются претензия, обычный вопрос, нейтральное обсуждение ошибки и цитирование. Сторона автора учитывается явно.
- [ ] Результат проходит общую проверку схемы и оснований, получает объяснимый приоритет и сохраняется без дублей.
- [ ] Работают фильтр типа и просмотр карточки с рекомендацией, источниками и ограничениями; ошибки классификации сохраняются для сравнения.
- [ ] Детектор использует общий воспроизводимый вход и метаданные запуска; другие типы продолжают работать.

**Исключения:** универсальная оценка настроения, прогнозирование оттока и автоматическая отправка клиенту.

## M1-10. Дать менеджеру четыре действия с сохранением истории

**AF-ID:** AF-017 часть 3, AF-019 часть 3. **GitHub:** [#17](https://github.com/alkselsv/ActionFlow/issues/17). **Blocked by:** [#13](https://github.com/alkselsv/ActionFlow/issues/13).

**Что построить:** менеджер подтверждает находку, отклоняет, откладывает или закрывает карточку; повторный анализ сохраняет его решения.

**Критерии приёмки:**

- [ ] Все четыре действия выполняются через UI и backend по модели M0, сохраняют автора, время и необходимые параметры решения. Подтверждение находки отделено от закрытия.
- [ ] Система может предложить закрытие с основаниями; переход завершает менеджер. Новые основания после закрытия, отклонения или откладывания обрабатываются по согласованным переходам.
- [ ] Повторная доставка запроса и действие по устаревшей версии карточки обрабатываются без потери истории и противоречивых переходов.
- [ ] Новые запуски и кандидаты не перезаписывают решения; дедупликация и связь обязательства с карточкой сохраняются.
- [ ] Фильтры статуса, счётчики и история карточки соответствуют сохранённым решениям; поведение одинаково для согласованных типов кандидатов. Итоговая проверка на трёх детекторах входит в M1-11.

**Исключения:** несколько менеджеров, внешние действия и автоматическое закрытие ситуации.

## M1-11. Сравнивать полные запуски и измерять базовое качество

**AF-ID:** AF-018 часть 3, AF-020. **GitHub:** [#18](https://github.com/alkselsv/ActionFlow/issues/18). **Blocked by:** [#15](https://github.com/alkselsv/ActionFlow/issues/15), [#16](https://github.com/alkselsv/ActionFlow/issues/16), [#17](https://github.com/alkselsv/ActionFlow/issues/17).

**Что построить:** единая кнопка запускает все три типа анализа, менеджер сравнивает результаты, а исторический набор даёт базовый отчёт качества.

**Критерии приёмки:**

- [ ] Полный запуск сохраняет вход, версии, результаты трёх типов, ошибки, стоимость и длительность. Частичный сбой виден; запуск не выдаёт неполный результат за полный успех.
- [ ] Сравнение одинакового входного среза показывает различия находок и оснований, сохраняя историю решений менеджера. Предыдущие запуски доступны после изменения настроек.
- [ ] Определено и реализовано сопоставление результатов с разметкой; отчёт содержит precision/recall по типам, корректность оснований, дубли, ошибки SLA, длительность и доступную стоимость.
- [ ] Повторное исполнение детектора для оценки отделено от replay workflow Temporal. Будущая информация исключена в пределах доступной истории, ограничения экспорта отражены в отчёте.
- [ ] Проверены перезапуск worker, ошибка провайдера, частичное сохранение и повтор после сбоя на полном пользовательском цикле; история и идентичность сохраняются.

**Исключения:** подбор лучшей модели, окончательные пороги живого пилота и эксперимент Cognee — это M2.

## M1-12. Подготовить эксплуатацию эксперимента и восстановление данных

**AF-ID:** AF-021. **GitHub:** [#19](https://github.com/alkselsv/ActionFlow/issues/19). **Blocked by:** [#17](https://github.com/alkselsv/ActionFlow/issues/17).

**Что построить:** выбранное в M0 окружение позволяет менеджеру безопасно работать с очередью и восстанавливать сохранённые данные и решения после сбоя.

**Критерии приёмки:**

- [ ] Работают согласованные вход и доступ; размещение, обработка данных, секреты и хранение соответствуют условиям M0.
- [ ] Практически проверены резервное копирование и восстановление прикладной БД и необходимых состояний исполнения по выбранной схеме. Перезапуск компонентов не теряет сохранённые решения.
- [ ] По идентификатору запуска находятся состояние и ошибка, доступность worker и внешнего провайдера диагностируется; логи не включают реальную переписку без необходимости.
- [ ] Документированы старт, конфигурация, проверки, диагностика, восстановление и удаление экспериментальных данных. На этом этапе достаточно одного сквозного детектора; полный набор проверяется при приёмке.

**Исключения:** высокая доступность SaaS, несколько компаний, инфраструктура живого бота и финальная приёмка качества.

## M1-13. Провести приёмку офлайн-MVP с менеджером

**AF-ID:** AF-022. **GitHub:** [#20](https://github.com/alkselsv/ActionFlow/issues/20). **Blocked by:** [#18](https://github.com/alkselsv/ActionFlow/issues/18), [#19](https://github.com/alkselsv/ActionFlow/issues/19). **Участие:** менеджер с подготовкой агента.

**Что получить:** протокол первого эксперимента с проверкой всех критериев MVP, базовыми метриками и замечаниями менеджера.

**Критерии приёмки:**

- [ ] Менеджер проходит импорт, настройки, запуск, очередь, основания и все четыре действия на согласованных данных.
- [ ] Проверены восемь функциональных критериев спецификации: импорт без дублей, ручные настройки, запуск/ошибки, три типа, разделение реакции и решения, неполные данные, история действий, сравнение запусков.
- [ ] Проверены повторный импорт и повторный анализ после решений менеджера; данные и история не теряются. Использовано восстановленное или перезапущенное окружение по сценарию M1-12.
- [ ] Сохранены базовые метрики, ошибки, ограничения и обратная связь; отдельно перечислены необходимые исправления и решения для M2.
- [ ] Менеджер подтвердил результаты функциональной приёмки. Готовность к живому пилоту не объявляется до проверки M2.

**Вопросы человеку:** время проведения, выбранные проекты/переписки, оценка удобства очереди и полезности находок. Агент не подтверждает пользовательскую приёмку от имени менеджера.

**Исключения:** подключение бота и расширение согласованного MVP.
