# AF-026, часть 1. Подготовка Telegram-бота и тестовой группы

Дата: 2026-11-23. Задача: [#27](https://github.com/alkselsv/ActionFlow/issues/27). Следующая задача: [#28 — проверка доступа, событий и сопоставления](../ROADMAP.md#af-026-проверить-доступ-бота-и-сопоставление-с-экспортом).

**Статус: подготовлены инструкции и проверка; создание бота, группы и передача токена требуют действий ответственного человека.** Пока эти действия не выполнены, #27 не закрывается, а бот не считается подключённым. Реальный клиентский пилот этим документом не включается.

## 1. Роли и ответственность

| Роль | Кто | Ответственность |
| --- | --- | --- |
| Владелец бота | владелец проекта | Создаёт бота через BotFather, владеет токеном, принимает решение об отзыве |
| Администратор тестовой группы | владелец проекта или явно назначенный человек | Создаёт закрытую группу, добавляет/удаляет бота и участников, меняет права |
| Ответственный за доступы | владелец проекта | Хранит токен вне Git, ротирует его, проверяет, что секрет не попал в Issues и логи |
| Тестовый участник | только синтетический/обезличенный участник | Пишет разрешённые тестовые сообщения, не приглашает реальных клиентов |

Если роли распределены между людьми, их имена и способ связи фиксируются в локальной записи вне Git. В репозиторий попадают только роли и обязанности, без токенов, телефонов и реальных имён клиентов.

## 2. Создание изолированной тестовой группы

1. Создайте отдельную **закрытую** группу, например `ActionFlow Test — synthetic`. Не используйте существующую клиентскую группу и не пересылайте в неё реальные переписки.
2. Добавьте только владельца, администратора и тестовых участников. Публичная ссылка-приглашение не нужна; доступ выдаётся адресно и отзывается после проверки.
3. Зафиксируйте назначение группы: техническая проверка Telegram Bot API, сопоставление с импортом и будущие синтетические события #28. Группа не является клиентским пилотом.
4. Проверьте, что участники понимают: сообщения тестовые, их можно цитировать в обезличенном виде; реальные имена, телефоны и переписки запрещены.
5. Не добавляйте бота в клиентские группы в рамках #27.

## 3. Создание бота и доступ

1. Владелец открывает BotFather в Telegram и создаёт отдельного бота командой `/newbot` (или выбирает уже существующего тестового бота, если он не используется в production).
2. Запишите только несекретные сведения: username бота, дату создания и ответственного. Токен не пересылайте в чат проекта, Issue или PR.
3. Добавьте бота в закрытую тестовую группу. Администратор группы назначает только права, необходимые для проверки; отправка сообщений клиентам не требуется.
4. В #28 отдельно проверить, достаточно ли выбранного режима видимости для получения текстовых сообщений и ответов. Если Telegram не отдаёт нужные события без дополнительных прав, это фиксируется как ограничение, а права не расширяются автоматически.
5. Администратор группы указывает, кто может менять название, участников, invite-ссылку и права бота. Эти действия не выполняются ботом.

## 4. Хранение токена

Рекомендуемый локальный вариант для текущего контура:

1. Скопируйте `.env.example` в локальный `.env` (файл уже исключён `.gitignore`).
2. Заполните в `.env`:

```text
TELEGRAM_BOT_TOKEN=<токен>
TELEGRAM_TEST_CHAT_ID=<отрицательный ID тестовой группы>
```

3. Не вставляйте значения в GitHub Issues, PR, документацию, скриншоты или логи. Для проверки используйте скрипт, который не печатает токен.
4. Если политика владельца требует OS secret store, храните токен там и передавайте его процессу через окружение. `.env` остаётся только локальным шаблоном конфигурации.
5. Перед коммитом проверяйте `git status` и `git diff --cached`; `.env` не должен быть отслеживаемым.

Ответственный за доступы проверяет, что токен не попал в Git и историю. При подозрении на утечку токен немедленно отзывается, а не «прячется» новым коммитом.

## 5. Отзыв и замена

- Владелец бота отзывает токен через BotFather (`/revoke`) или удаляет тестового бота, если он больше не нужен.
- Новый токен записывается только в локальное хранилище; все прошлые значения считаются скомпрометированными.
- После замены перезапускается будущий коннектор #28 и повторяется проверка доступа; старые сообщения и история не переписываются.
- Ответственный за отзыв и замену — владелец бота; администратор группы подтверждает, что бот остался в группе или удалён осознанно.

## 6. Тестовые сценарии для #28

В тестовой группе нужно подготовить синтетические примеры, достаточные для сверки с импортом:

| Сценарий | Что сделать | Что проверить в #28 |
| --- | --- | --- |
| Текст | Обычное сообщение клиента и ответ сотрудника | ID, автор, время, сторона |
| Ответ | Ответ на конкретное сообщение | `reply_to` и связь с исходным ID |
| Редакция | Изменить текст сообщения после отправки | Доступна ли редакция и как она соотносится с импортом |
| Нетекстовый элемент | Фото/файл/голосовое с подписью или без | Ограничение «содержимое не обработано» |
| Новое сообщение | Отправить после первого чтения | Событие приходит один раз или повторяется с понятным признаком |
| Потеря доступа | Удалить бота из группы или изменить права | Система замечает потерю, а не считает тишину отсутствием ответа |
| Другой проект | Отдельная тестовая группа/проект | Нет смешивания чатов и участников |

Тексты должны быть синтетическими и не содержать реальных клиентских данных. Для редакции и удаления заранее записать, что именно поддерживает Telegram; отсутствие истории не компенсируется догадкой.

Готовые тексты для ручной отправки в тестовую группу:

| № | Действие | Текст/вложение | Ожидаемая проверка |
| ---: | --- | --- | --- |
| 1 | Клиент отправляет | `Нужно прислать подписанную смету к пятнице.` | Новый `unanswered`-контекст; исходный ID |
| 2 | Сотрудник отвечает №1 | `Пришлю подписанную смету в пятницу до 12:00.` | `reply_to` и `commitment` |
| 3 | Сотрудник редактирует №2 | `Пришлю подписанную смету в пятницу до 15:00.` | Доступная редакция и новый срок |
| 4 | Сотрудник отправляет файл | Файл + подпись `Подписанная смета.` | Нетекстовый элемент и ограничение содержимого |
| 5 | Клиент отвечает №3 | `Получили, спасибо. Ждём подтверждения отправки.` | Цепочка ответа и отсутствие ложного закрытия |
| 6 | Администратор меняет права/удаляет бота | Без сообщения в группе | Потеря доступа видна в #28, а не маскируется тишиной |

Редакция №3 должна быть выполнена после первого чтения, чтобы проверить именно доступную правку. Для удаления сообщения заранее зафиксировать ожидаемое поведение Telegram; не выдавать отсутствие tombstone за восстановленную историю.

## 7. Проверка подготовки

После добавления бота в группу и заполнения `.env`:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\check-telegram-setup.ps1
```

Скрипт:

- проверяет, что `.env` исключён из Git и токен не встречается в отслеживаемых файлах;
- вызывает Telegram `getMe`, не печатая токен;
- проверяет доступ к тестовой группе через `getChat` и членство бота через `getChatMember`;
- выводит только ID/username бота, тип и название группы, статус и признаки прав;
- не отправляет сообщения и не читает переписку.

Если бот является участником, но не администратором, скрипт выдаёт предупреждение. Достаточность видимости проверяется в #28; не расширяйте права только ради успешного вывода скрипта.
