# AF-001: формат входа и проверочные примеры

Дата: 2026-11-20. Статус: часть 2 AF-001, [issue #3](https://github.com/alkselsv/ActionFlow/issues/3). Связанные документы: [исходные данные](af-001-source-data.md), [политика окружения](af-004-environment-policy.md), [fixtures](../../data/fixtures/telegram/README.md).

## Границы

Документ описывает формат, который импортёр принимает для проектирования и проверки. Он опирается на согласованный синтетический набор, а не на реальный экспорт Telegram: фактическая схема Telegram Desktop export не проверялась и на этом этапе недоступна.

Поэтому ниже явно разделены:

- **подтверждено набором** — свойство, которое есть в fixtures и проверяется скриптом;
- **предположение** — поведение, которое нужно для проектирования, но не подтверждено реальными данными. Импортёр обязан обрабатывать такие поля без падения и не выдавать предположение за факт.

## Структура файла

Один файл — один чат:

```json
{
  "name": "Synthetic ...",
  "type": "private_group",
  "id": 200002,
  "messages": [],
  "_actionflow_fixture": {
    "synthetic": true,
    "workspace_id": "edge",
    "conversation_id": "format",
    "source_record_count": 3,
    "source_export_format": "synthetic fixture",
    "not_a_real_telegram_export": true,
    "import_sequence": 1,
    "reimport_of": "optional file name"
  }
}
```

`_actionflow_fixture` — служебный блок fixtures. В реальном экспорте его нет; импортёр не должен зависеть от него в production-коде. Неизвестные верхнеуровневые поля (например, `about`, `personal_information`) нужно игнорировать, а не считать ошибкой формата.

## Поля сообщения

| Поле | Статус | Смысл и нормализация |
| --- | --- | --- |
| `id` | подтверждено | Локальный идентификатор сообщения. Уникален внутри чата; не обязан быть непрерывным или глобально уникальным. Порядок в файле считается хронологическим, но импортёр сортирует по `date_unixtime`, затем по `id`. |
| `type` | подтверждено для `message`; предположение для `service` | `message` — обычное сообщение, `service` — системное событие. Неизвестный тип сохраняется как системное событие с исходным значением, а не отбрасывается молча. |
| `date` | подтверждено | ISO-время. В fixtures хранится UTC; в реальном экспорте предполагается локальное время чата. Для расчётов использовать `date_unixtime`, исходное значение сохранять. |
| `date_unixtime` | подтверждено | Unix-время в секундах, строка. Основной источник времени отправки. |
| `from`, `from_id` | подтверждено | Автор и его идентификатор. `from_id` уникален внутри чата; в fixtures имеет вид `userNNNN`, в реальном экспорте — числовой суффикс. Сторона автора берётся из настроек проекта, а не из имени. |
| `text` | подтверждено | Строка или массив частей. Массив склеивается в текст без разделителя; форматирование (`bold`, `italic`, `link` и др.) сохраняется отдельно и не теряется при поиске. Пустое/отсутствующее значение допустимо для медиа и системных событий. |
| `text_entities` | предположение | Альтернативная форма форматирования Telegram. Если появится, импортёр должен сохранить типы, текст и `href`, не считая поле ошибкой. |
| `reply_to_message_id` | подтверждено | Ссылка на сообщение в том же чате. Если цель отсутствует в загруженном окне, ссылка остаётся неразрешённой и попадает в отчёт импорта; выдумывать цель нельзя. |
| `edited`, `edited_unixtime` | предположение | Признак наблюдённой редакции. Экспорт даёт только последний текст, не историю. Импортёр увеличивает `revision`, сохраняет новое наблюдение и не перезаписывает старые основания. |
| `forwarded_from` | предположение | Метка источника пересылки. Не меняет сторону автора сообщения в текущем чате. |
| `photo`, `file`, `voice_message`, `video_message`, `sticker` | предположение | Наличие нетекстового содержимого. Содержимое не анализируется; сохраняются тип, ссылка и доступные метаданные. Подпись к медиа остаётся в `text`. |
| `media_type`, `mime_type`, `duration_seconds` | предположение | Метаданные вложения. Неизвестный `media_type` сохраняется как есть и отражается в отчёте, а не отбрасывается. |
| `actor`, `actor_id`, `action`, `members`, `title` | предположение для `service` | Системное событие: кто и что сделал. `actor` не становится участником со стороной; неизвестное `action` сохраняется. |
| `_actionflow_synthetic_source` | только fixtures | `external_id`, `revision`, `sender_role`, `sent_at`, `observed_at`, `reply_to_external_id`, `source`. Не часть реального экспорта. |

## Идентичность и связи

- Идентичность сообщения — пара `(внешний ID чата, внешний ID сообщения)`. Внутри одного чата `id` уникален; между чатами совпадения допустимы.
- `external_id` в fixtures — стабильный идентификатор исходной записи; он не равен локальному `id` и используется для сопоставления при повторной загрузке. В реальном экспорте отдельного `external_id` нет: его роль выполняет `id` сообщения внутри чата.
- Ссылка ответа разрешается только внутри того же чата. Ссылки на сообщения вне загруженного среза сохраняются как неразрешённые.
- Хронология восстанавливается по `date_unixtime`, затем по `id`. Если порядок в файле нарушен, импортёр сортирует, но фиксирует факт нарушения в отчёте.
- Основания анализа привязываются к наблюдённой редакции сообщения, а не к «текущему тексту» без версии.

## Время

- `date_unixtime` — авторитетное время отправки.
- `date` сохраняется как исходное представление. В fixtures это UTC, в реальном экспорте предполагается локальное время чата; смешивать их нельзя.
- Часовой пояс проекта задаётся вручную. Импортёр не выводит его из `date`, если offset отсутствует.
- `observed_at` — время, когда система увидела сообщение или редакцию. Оно не равно времени отправки и не должно подменяться им.

## Текст и форматирование

- Строка и массив частей дают один и тот же текст для поиска и анализа.
- Части-объекты сохраняются как форматирование: тип, текст, `href`. Ссылка не должна попадать в текст только потому, что у неё есть `href`.
- Пустой текст допустим для фото без подписи, голосового, файла и системного события.

## Вложения и голосовые

- Наличие вложения фиксируется; содержимое не анализируется в первом эксперименте.
- Если ответ может находиться во вложении, результат отражает ограниченную полноту данных.
- Подпись к фото/файлу остаётся текстом сообщения и участвует в анализе.
- Реакции, опросы и кнопки в текущем наборе не представлены; неизвестные поля сохраняются без интерпретации.

## Системные события

- `type: "service"` нормализуется в системное событие, а не в сообщение участника.
- `actor`/`actor_id` — источник события; сторона к нему не применяется. Если актор неизвестен, это отображается явно.
- Известные действия (`join_group`, `leave_group`, `invite_members`, `change_title`) и неизвестные действия сохраняются с исходным `action`.
- Системное событие не создаёт обращение и не считается реакцией Vedita.

## Редакции и удаления

- Экспорт не является полной историей изменений. Доступна только редакция, попавшая в выгрузку или наблюдённая системой.
- `edited`/`edited_unixtime` означают последний известный текст; предыдущий текст не восстанавливается.
- При повторной загрузке `revision` увеличивается, `observed_at` обновляется, старое основание остаётся доступным.
- Удаления: если сообщение исчезло из нового экспорта, импортёр не удаляет его молча и не выдумывает причину; факт отсутствия фиксируется как ограничение данных.

## Повторная загрузка

Пример: `edge-reimport-s-006-first.json` → `edge-reimport-s-006-second.json`.

Ожидаемое поведение:

1. Сообщения сопоставляются по внешнему ID сообщения внутри внешнего ID чата (в fixtures — `external_id`, в реальном экспорте — `id` сообщения), а не по позиции в файле.
2. Совпавшие сообщения не дублируются; обновляются `observed_at` и, при наличии, редакция.
3. Изменённое сообщение получает `revision: 2`; прежняя редакция остаётся в истории.
4. Новое сообщение добавляется.
5. Пропавшее сообщение не удаляется автоматически; фиксируется в отчёте.
6. Ранее принятые решения менеджера не перезаписываются.

## Состав и достаточность

- Согласованный набор эксперимента: 9 чатов, 43 сообщения ([AF-001](af-001-source-data.md)).
- Проверочные примеры формата: 6 файлов, 5 разговоров, 24 записи (21 уникальное сообщение; вторая загрузка повторяет 3 сообщения).
- Всего в `data/fixtures/telegram/`: 15 файлов, 14 разговоров, 67 записей.

Покрыто: обычный текст, составной текст и форматирование, ответы, неизвестный участник, фото/файл/голосовое/видео/стикер, системные события, редакция, пересылка, повторная загрузка и дедупликация.

Не покрыто и должно проверяться в импортёре отдельно или новыми синтетическими примерами: удалённые сообщения, несколько последовательных редакций, нарушенный порядок и дубликаты `id`, повреждённый/частичный файл, очень большой чат, отсутствие часового пояса, реакции/опросы/кнопки, боты и каналы, несколько часовых поясов.

Набор достаточен для проектирования импорта и сохранения оснований по перечисленным случаям. Он не доказывает реальную схему Telegram export и не заменяет production-импортёр.

## Проверка

```text
python scripts/validate_fixtures.py
```

Ожидаемый результат:

```text
OK: 15 files, 14 conversations, 67 message records, 1 re-import pair(s)
```

Скрипт проверяет разбор JSON, отсутствие BOM, пометку синтетического набора, уникальность `id`/`external_id`, порядок, время и редакции, разрешимость ответов, роли, допустимые типы сообщений и вложений, повторную загрузку и отсутствие контактных данных.
