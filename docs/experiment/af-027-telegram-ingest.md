# AF-027, часть 1. Приём новых сообщений Telegram в проект

Дата: 2026-11-23. Задача: [#29](https://github.com/alkselsv/ActionFlow/issues/29). Предыдущая проверка: [AF-026](af-026-telegram-access.md). Следующая часть: [#30](https://github.com/alkselsv/ActionFlow/issues/30).

**Статус: ручное подключение, нормализация и приём реализованы; проверка выполнена на синтетических Bot API updates. Реальный клиентский чат и LLM-анализ новых событий не включались.**

## 1. Выбранный путь

Для тестового контура используется только Bot API `getUpdates` с long polling. Webhook не реализован, поэтому два транспорта не конкурируют. Один процесс коннектора читает updates для одного бота, проверяет разрешённый чат и пишет сообщения в ту же модель `Message`/`MessageRevision`, что и импорт экспорта.

Поток:

```text
getUpdates(offset)
  -> проверка update_id и типа события
  -> поиск ручного подключения по устойчивому chat_id
  -> нормализация сообщения/редакции/вложения
  -> запись Message + Revision
  -> сохранение offset в той же транзакции
```

Чтение отделено от отправки: коннектор не вызывает `sendMessage` и не требует права отправки. Токен читается только из `TELEGRAM_BOT_TOKEN`; URL Telegram не печатается, ошибки клиента не содержат токена.

## 2. Ручное подключение проекта

В веб-интерфейсе проекта есть панель «Telegram-бот · тестовый чат». Менеджер вводит:

- устойчивый числовой ID чата, полученный при проверке #28;
- необязательное название для отображения.

ID — единственный ключ связи; название и username не используются. Подключение создаёт или переиспользует `Chat` с парой `(source="telegram", external_id=<ID>)` и запись `telegram_connection`.

Ограничения:

- один чат — один проект (`Chat.project_id` уникален);
- если ID уже связан с другим проектом, возвращается `409`;
- если у проекта уже есть другой Telegram-чат, возвращается `409`;
- отключение переводит связь в `disconnected`, история и сообщения сохраняются;
- события от неизвестного или отключённого чата отклоняются.

API:

```text
GET  /api/v1/projects/{project_id}/telegram
POST /api/v1/projects/{project_id}/telegram/connect
POST /api/v1/projects/{project_id}/telegram/disconnect
```

`bot_configured` в ответе показывает только наличие токена в локальном окружении и никогда не возвращает сам токен.

## 3. Нормализация

Поддерживаемые обновления: `message`, `edited_message`, `my_chat_member`. Неизвестные типы не создают сообщений и учитываются как отклонённые.

| Telegram Bot API | Модель |
| --- | --- |
| `message.chat.id` | `Chat.external_id` |
| `message.message_id` | `Message.external_id` |
| `message.date` | `Message.sent_at` |
| `message.from.id` | `Participant.source_author_id` |
| `message.text` / `caption` | `MessageRevision.snapshot.text` |
| `message.entities` / `caption_entities` | `text_format` |
| `reply_to_message.message_id` | `reply_to_external_id` |
| `edit_date` | `edited_at` |
| `photo`, `document`, `voice`, `video`, `video_note`, `sticker`, `audio`, `animation` | непустые `attachments` с `media_type`; содержимое не обрабатывается |
| `my_chat_member.new_chat_member.status` | состояние подключения: `active` или `needs_check` |

Источник каждой наблюдённой редакции сохраняется в snapshot как `source_kind="telegram_bot"`; у импорта — `telegram_import`. Это позволяет отличить способы получения и корректно сравнивать одинаковый текст без ложной редакции из-за разных форматов entities.

Неизвестная сторона не угадывается. После появления участника его ID и имя отображаются в настройках проекта со стороной `unknown`; менеджер задаёт `vedita` или `customer` вручную.

## 4. Граница сохранения и подтверждения

`getUpdates` подтверждает update, когда следующий запрос использует `offset` больше его `update_id`. Коннектор:

1. читает текущий `last_update_id` из `telegram_bot_state`;
2. запрашивает updates начиная со следующего;
3. пишет сообщения, редакции и новый offset в одной транзакции;
4. только после успешного commit следующий запрос подтверждает пакет.

Если запись падает посередине, транзакция откатывается, offset не двигается, и пакет будет получен повторно. Это проверено тестом с искусственным сбоем на втором сообщении: после отката нет ни сообщений, ни cursor.

Повторная доставка:

- точный повтор уже обработанного update пропускается по идентификатору и отпечатку;
- повторное сообщение с тем же `(chat_id, external_id)` не создаёт новый `Message`;
- одинаковая редакция не создаёт новую `MessageRevision`;
- новая редакция сохраняется отдельно, прежняя остаётся доступной по `revision_id` и в списке редакций.

Пересечение импорта и бота проверено на одинаковом `chat_id` и `message_id`: исходная импортированная редакция не дублируется, последующая редакция бота сохраняет старую версию. Повторный импорт старого экспорта после редакции не откатывает текущую редакцию.

## 5. Ошибки и потеря доступа

- неизвестный чат: событие отклоняется, не попадает ни в один проект;
- отключённый чат: событие отклоняется;
- некорректное сообщение (например, нет `date`): отклоняется, подключение переводится в `needs_check`;
- `my_chat_member` со статусом `left`/`kicked`: подключение переводится в `needs_check` с причиной `bot_left`;
- возврат бота в группу: `active`;
- ошибка Bot API: коннектор записывает безопасный код. Только временные ошибки и ограничения частоты повторяются автоматически.

`needs_check` показывает проблему источника. В карточке подключения видны последнее наблюдение чата, последний успешный опрос, задержка и известные интервалы неполноты. Полнота истории остаётся неизвестной и при успешном опросе.

### Восстановление и сверка (#30)

1. Запускайте один процесс опроса на токен. После короткого простоя перезапустите коннектор с той же БД и токеном. Он продолжает обработку доступной очереди. Подтверждение событий через offset следует за фиксацией транзакции. Повторная доставка проверяется по идентификатору и отпечатку события, поэтому ранее не обработанное позднее событие сохраняется.
2. При временной ошибке коннектор повторяет опрос с паузами 2, 4, 8 и 16 секунд, учитывая более долгую паузу `retry_after` при ограничении частоты. После пятой неудачи или постоянной ошибки процесс завершается с ненулевым кодом. Панель показывает причину, число попыток и срок паузы, если он задан. После устранения причины запустите процесс снова.
3. Если с последней выгрузки очереди прошло больше окна хранения, панель показывает интервал, который очередь уже не покрывает. Полный пакет из 100 событий подтверждает работу опроса, но не завершение выгрузки. Когда коннектор дочитывает очередь, запись об интервале сохраняется. После длительного отсутствия событий он опрашивает очередь без старого offset, чтобы Telegram мог вернуть событие с новым диапазоном ID. [Окно хранения и ID обновлений в Bot API](https://core.telegram.org/bots/api#getting-updates)
4. При событии о выходе или отсутствии членства проверьте права в разрешённой тестовой группе. Возврат членства завершает интервал потери доступа. Ручное отключение и возобновление фиксируются отдельно. Пустой ответ Telegram сам по себе не меняет членство и не удаляет сообщения.
5. Для сверки экспортируйте доступную историю **того же чата** в Telegram Desktop и импортируйте JSON в «Переписку» существующего проекта. Сверьте нужные даты, сообщения и редакции по идентификаторам. Повторный импорт использует ту же идентичность сообщения и сохраняет наблюдаемые редакции. Панель показывает время импорта, а пробел остаётся в истории, поскольку экспорт не доказывает полноту.

Технические проверки воспроизводятся синтетическими ответами транспорта. Они охватывают короткий перерыв и повтор с прежней БД, смену диапазона ID, истечение окна, повторы и потерю членства. Работа с клиентским потоком требует отдельного допуска.

Ограничения, унаследованные от выбранного транспорта: Bot API не гарантирует получение сообщений, которых не видел бот, не даёт полноценной истории удалений и хранит ожидающие updates ограниченное время. Редакция отображается только если Telegram её доставил. Удаление сообщения не реконструируется.

## 6. Запуск коннектора

Токен хранится в локальном `.env` или OS secret store; не коммитится и не вставляется в Issue:

```text
TELEGRAM_BOT_TOKEN=<токен>
```

После ручного подключения чата в интерфейсе:

```powershell
$env:PYTHONPATH = 'backend/src'
uv run --project backend --frozen python -m actionflow.telegram_connector
```

Для однократной проверки:

```powershell
uv run --project backend --frozen python -m actionflow.telegram_connector --once
```

Долгий polling можно настроить через `ACTIONFLOW_TELEGRAM_POLL_TIMEOUT_SECONDS` (по умолчанию 30 секунд). Коннектор не отправляет сообщения и не печатает токен. После получения событий нажмите «Обновить переписку» в проекте или откройте проект заново.

## 7. Проверки

Интеграционные тесты: `backend/tests/integration/test_telegram_events.py`.

Проверено:

- ручное подключение, конфликт чатов и валидация ID;
- разделение двух проектов и отклонение неизвестного чата;
- текст, ответ, стикер и редакция;
- сохранение прежней редакции;
- неизвестная сторона и её ручное уточнение;
- повторная доставка без дублей и канонический cursor;
- некорректное событие и `needs_check`;
- потеря/возврат членства бота;
- откат при частичном сбое и повтор после него;
- пересечение импорта и Bot API;
- `poll_once`: offset до запроса и подтверждение после commit.
