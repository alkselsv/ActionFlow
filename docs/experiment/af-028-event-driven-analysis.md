# AF-028 ч. 1: анализ по новым Telegram-событиям

Дата: 2026-11-23. Задача: [GitHub #31](https://github.com/alkselsv/ActionFlow/issues/31).

## Запуск и транзакции

После ручного подключения тестовой группы Bot API updates записываются в общую
модель сообщений и редакций. Анализ запускают новые пользовательские сообщения
и действительно изменившиеся редакции; служебные сообщения группы не запускают
детекторы. В той же транзакции, что сообщение, receipt и
cursor, для нового сообщения или действительно изменившейся редакции
создаётся либо обновляется `AnalysisRun` и `OutboxEvent`. Повторный update
отсекается по receipt; неизменившаяся редакция не создаёт новый анализ.
Ошибка commit откатывает и событие, и запрос анализа, поэтому Telegram сможет
повторить update.

Dispatcher запускает существующий `AnalysisWorkflow` по `workflow_id`. Повтор
запуска workflow безопасен благодаря стабильному ID, а outbox остаётся в БД
после перезапуска dispatcher. Для одного проекта dispatcher блокирует
одновременный старт второго workflow до завершения первого. Если событие
приходит после старта workflow, оно создаёт следующий запуск; уже сохранённый
вход анализа не перезаписывается.

## Объединение событий и настройка

Автоматический запуск выключен по умолчанию. Для разрешённого тестового
окружения его можно включить локально:

```dotenv
ACTIONFLOW_TELEGRAM_AUTO_ANALYSIS_ENABLED=true
ACTIONFLOW_TELEGRAM_ANALYSIS_DEBOUNCE_SECONDS=10
```

Приёмка использует 10-секундное окно тишины: пока запуск не ушёл из pending,
близкие новые сообщения и редакции объединяют его, сдвигая `as_of` и срок
диспетчеризации. Значение ограничено диапазоном 0–300 секунд. Настройки
клиентского пилота должны быть согласованы отдельно до включения.

Автоматический срез охватывает доступную историю подключённого чата от
первого сохранённого сообщения до времени последнего события. Анализ проходит
через обычный лимит входа в 50 000 сообщений. Время периода, настройки проекта,
revision и контекст фиксируются в `AnalysisRun`/`AnalysisInputMessage`.

## Очередь, полнота и ошибки

Результаты используют существующие три детектора и тот же механизм очереди
ситуаций; подтверждённые обязательства, решения менеджера и новые кандидаты
остаются разными сущностями. При подготовке входа run получает счётчики
необработанных вложений, неизвестных участников, доступных сообщений и
неполноты истории, а также статус Telegram-подключения и известные интервалы
пробелов. Пустая или неполная история сама по себе не доказывает отсутствие
ответа.

Temporal выполняет ограниченные повторы временных ошибок Activities. Ошибка
модели сохраняется в статусе запуска и видна менеджеру; последующее новое
событие создаёт следующий идемпотентный запуск. Уведомления и расписания
проверок не входят в эту часть AF-028.

## Проверки реализации

- повтор update не создаёт повторный запуск;
- новая редакция в debounce-окне объединяется с pending запуском;
- редакция после старта анализа ставит отдельный follow-up;
- dispatcher не запускает параллельные workflow одного проекта;
- сохранённые Telegram gaps попадают в limitations входа;
- автоматический анализ выключен без явной настройки;
- модельные повторы/ошибки и повтор dispatcher покрываются существующим
  Temporal/outbox контуром.

## Snapshot receipt cutoff

`input_received_at` records the latest event included in a pending coalesced run. Input preparation uses this timestamp to select message revisions and source observations. The cutoff advances only while the run is pending; after dispatch, the resulting input snapshot is immutable. Existing runs fall back to `created_at`.
