# AF-028. Контроль сроков и плановые сверки

Тикет [#32](https://github.com/alkselsv/ActionFlow/issues/32) дополняет [анализ по событиям](af-028-event-driven-analysis.md). Коннектор и dispatcher продолжают использовать существующий outbox. Расписания создаёт оператор в тестовом контуре.

## Запуск и управление

После миграции `0014_deadline_observation` запустите API, dispatcher и worker по инструкции из README. Для управления расписаниями из корня репозитория используйте команды.

```powershell
$env:PYTHONPATH = 'backend/src'
uv run --project backend --frozen python -m actionflow.telegram_schedules install --reconciliation-minutes 60
uv run --project backend --frozen python -m actionflow.telegram_schedules status
uv run --project backend --frozen python -m actionflow.telegram_schedules pause
uv run --project backend --frozen python -m actionflow.telegram_schedules resume
```

Расписание сроков запускает короткое окно каждые пять минут. Внутри окна durable timer просыпается в ближайший известный срок или через 30 секунд для переоценки изменившихся ожиданий. Каждое окно заканчивается через 270 секунд и оставляет ограниченную историю Temporal. Сроки на дни и недели сохраняются в БД между окнами. Следующее окно подбирает сроки, наступившие во время простоя. Worker после перезапуска продолжает незавершённое окно по истории Temporal.

Расписание сверки по умолчанию запускается раз в час. Частота задаётся при первом `install` в пределах 5–1440 минут. Повторный `install` сохраняет существующее расписание. Для изменения частоты обновите целое расписание сверки в Temporal либо в остановленном тестовом контуре пересоздайте его с нужным интервалом.

Оба расписания используют `SKIP`, чтобы активный запуск того же расписания не перекрывался новым. Окно догоняющего исполнения равно интервалу расписания. Activity выполняется максимум три раза в пределах одной минуты. Ошибка отдельного запуска видна в Temporal. Пауза блокирует новые окна, а начатое окно заканчивается в своём лимите. Отключение чата или состояние «Требует проверки» исключает проект из новых сверок и проверок сроков. Уже созданный анализ сохраняет свой вход. После восстановления подключения проверяются актуальные сохранённые сроки.

## Правила и наблюдаемость

- SLA использует сохранённую границу первого ответа. Ответ к границе включительно завершает отсчёт и сохраняет карточку открытой. Известный пробел или неопределённость до границы отмечаются как ограничение, когда по доступной истории нельзя подтвердить своевременную реакцию. Таймер не меняет решения менеджера.
- В Telegram-запусках версия SLA выбирается по времени исходного сообщения. Для срока обещания используется версия на момент обещания, для переноса — на момент сообщения о переносе. Новая версия календаря применяется к новым событиям. У отменённых и исполненных обязательств ожидание прекращается. История прежних сроков сохраняется в событиях обязательства.
- Проверка сериализуется с публикацией очереди на строках проекта и карточки. При уже поставленном анализе проверка откладывается. Просрочка обновляет текущую карточку, сохраняет отдельное наблюдение таймера и оставляет исторический запуск доступным.
- Сверка запускает обычный анализ по доступной в БД истории и фиксирует состояние подключения и известные интервалы неполноты. За один интервал создаётся максимум один запуск на проект. Если уже идёт анализ проекта, очередная сверка пропускается. Для восполнения доступной истории используется [дополнительный экспорт](af-027-telegram-ingest.md#восстановление-и-сверка-30).
- В истории можно отличить плановую сверку от ручного запуска и увидеть длительность и доступную стоимость. Используются локальные детекторы. Если стоимость вычисления неизвестна, интерфейс показывает «неизвестна». Проверки таймера работают с БД и не вызывают модель.
