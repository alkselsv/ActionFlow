# AF-026: протокол доступа и событий Telegram

Дата: 2026-11-23. Статус: предварительный технический протокол; живые
наблюдения в тестовой группе и сопоставление фактического экспорта ещё не
подтверждены. Тикет: [GitHub #28](https://github.com/alkselsv/ActionFlow/issues/28).

## Выбранный транспорт

Для изолированного теста и первого пилотного прототипа выбран Bot API
`getUpdates` с long polling. Он не требует публичного HTTPS endpoint и
позволяет контролируемо проверить входящие события. Webhook в этой конфигурации
не включается: Telegram считает способы взаимоисключающими. Для production
выбор подлежит отдельному пересмотру после допуска пилота; этот документ не
разрешает подключать реальные клиентские чаты.

Аутентификация Bot API выполняется токеном бота в HTTPS URL. Сам URL поэтому
содержит секрет: его нельзя писать в логи, shell history, Git или Issues.
Локальный probe получает токен только из переменной процесса
`TELEGRAM_BOT_TOKEN`, скрывает тело/URL ошибок, не выполняет `sendMessage` и
по умолчанию не подтверждает updates.

`getUpdates` возвращает ожидающие события. Повторный запрос может вернуть уже
полученное неподтверждённое событие. Telegram подтверждает update, когда новый
запрос имеет `offset` выше его `update_id`; после подтверждения прежние события
больше не возвращаются. Сохранять cursor следует только после надёжной записи
обработанных данных, а повторную доставку устранять по `update_id`. Telegram
хранит ожидающие updates не более 24 часов. `update_id` растёт последовательно
и помогает упорядочить поток, но не заменяет идентификаторы чата и сообщения.

## Видимость и права

- `getUpdates` читает только события, доступные конкретному боту. Чтение не
  требует права отправки сообщений.
- В группах privacy mode включён по умолчанию. В этом режиме обычные сообщения
  не гарантированы: бот получает команды, адресованные ему сообщения и
  соответствующие ответы. Для проверки всех сообщений в `TEST` владелец
  отключает privacy mode и повторно добавляет бота. Для теста достаточно
  обычного участника; назначать бота администратором не нужно.
- `my_chat_member` позволяет наблюдать собственное изменение членства бота.
  Необходимость прав администратора для прочих действий в группе проверяется
  отдельно. Отправка сообщений не входит в тест или пилотный контракт.
- Разрешённый набор обновлений для probe: `message`, `edited_message`,
  `my_chat_member`. Типы обновлений не запрашиваются двумя транспортами.

Официальные источники: [Telegram Bot API, Getting updates и Update](https://core.telegram.org/bots/api#getting-updates),
[Telegram Bot Features, Privacy Mode](https://core.telegram.org/bots/features#privacy-mode),
[Bots FAQ](https://core.telegram.org/bots/faq#what-messages-will-my-bot-get).

## Сопоставление с экспортом

Кандидат на ключ сообщения: `(chat_id, message_id)`. Ответ связывается внутри
того же чата по `reply_to_message_id`; автор — по числовому `from.id`, если
фактическая схема Telegram Desktop export содержит сопоставимый числовой
суффикс `from_id`. Имена и username не являются ключами. Время Bot API `date`
и `edit_date`, export `date_unixtime` и редакционные поля нужно сравнивать как
Unix-время, сохраняя исходные значения. Редактирование — новая наблюдаемая
версия, а не переписывание уже использованного основания.

Эти правила пока являются гипотезами для фактического экспорта: синтетические
fixtures проекта не подтверждают схему реального Telegram Desktop export.
Probe вычисляет digest текста только в памяти для сравнения и не записывает
его. В отчёт попадают псевдонимы ID с отдельным случайным ключом на каждый
запуск и метаданные событий; отчёт остаётся чувствительными локальными
данными. Если chat ID нельзя сверить однозначно или форма author ID отличается,
совпадение фиксируется как неразрешённое; объединять данные по одному имени
запрещено.

## Сценарий проверки и состояния

В изолированной приватной группе `TEST` (не клиентская) владелец создаёт
синтетические события: обычное сообщение; ответ на сообщение; редакцию;
стикер/безопасный файл; удаление и повторное добавление бота. Группа должна
содержать только владельца/тестовый аккаунт и бота; клиентские участники и
клиентские переписки запрещены. Сравнить экспорт этой группы и Bot API report
по доступным ID, ссылкам ответов, автору и времени. Экспорт, токен и
псевдонимный отчёт остаются в локальном профиле владельца, вне репозитория;
не прикладывать их к Issues или документации. Допустимо записать только
вручную проверенные агрегированные числа совпадений/неоднозначностей.

Probe никогда не подтверждает updates. При повторном запуске неподтверждённые
события могут прийти снова. Идентификаторы в отчёте получают случайные
псевдонимы с новым ключом в памяти на каждый запуск; отчёт остаётся
чувствительным и не считается анонимным. Probe одноразовый и не контролирует
состояние polling или cursor gaps со временем. Реальный consumer должен
сохранять обработанные данные до продвижения offset и убирать повторы по
`update_id`.

Пропажа ожидаемого тестового update, изменение `my_chat_member`, ошибка API,
непродвигающийся cursor или остановка polling переводят источник в состояние
`needs_check`; автоматически считать историю полной нельзя. Повторно получить
пропущенный период после 24 часов через Bot API нельзя гарантировать. Удаления
сообщений не обещаются: в обычном Bot API потоке нет надёжного универсального
события восстановления удалённой истории. Экспорт — отдельный ручной импорт,
а не механизм непрерывного восстановления.

В probe поле `chat_id_exact_match` показывает, совпал ли экспортный chat ID с
Bot API ID без преобразования. `chat_id_mismatch` означает, что одинаковое
числовое значение message ID найдено в Bot API updates, но точного chat ID
нет. Это только сигнал для проверки: message ID уникален лишь внутри чата, и
одинаковое число в другом чате может относиться к иному сообщению. Требуется
ручная проверка формата/преобразования по исходникам, сохранённым владельцем
локально. До подтверждения преобразования сообщения не связываются.

## Ручное подключение группы к проекту

Менеджер выбирает проект и целевую группу, проверяет устойчивый chat ID в
локальном отчёте и подтверждает связь явно. Система хранит ключ источника,
необходимые полномочия и историю подтверждения. Имя группы показывается только
для удобства. Если ID отсутствует или источник нельзя доказать, подключение и
слияние истории откладываются до ручного разрешения неоднозначности.

| Проверка | Результат |
| --- | --- |
| Официальная семантика long polling / ack / retention | Подтверждена документацией Telegram |
| Privacy mode и получение всех сообщений | Подтверждено документацией; настройка конкретного бота и группы ещё не проверена probe |
| Доставка message / reply / edit / non-text в `TEST` | Ожидает запуска probe после генерации свежих событий |
| Изменение членства и потеря доступа | Ожидает удаления/повторного добавления бота и проверки `my_chat_member` |
| Сопоставление ID и времён с фактическим Telegram Desktop export | Ожидает локального сравнения фактического JSON |
| Подключение группы к проекту без имени как ключа | Правило определено; UI/интеграция не входит в эту проверку |
