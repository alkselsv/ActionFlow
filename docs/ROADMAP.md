# Дорожная карта ActionFlow

Дата: 2026-11-19.

Назначение: основа для декомпозиции работ в GitHub Issues. План подготовлен по [спецификации первого эксперимента](specs/responseflow-mvp.md), [обзору прототипа](../PROTOTYPE.md) и [предметным терминам](../GLOSSARY.md).

Согласованные границы продукта определяет спецификация. Этот документ определяет порядок работ, зависимости, проверяемые результаты и условия перехода между этапами. Изменение требований сначала отражается в спецификации, затем в плане и связанных тикетах.

Все работы ниже запланированы; реализация и приёмка ещё не выполнены. Идентификаторы `AF-001` и далее — стабильные идентификаторы плана, а не номера GitHub Issues. Тикеты этим документом не создаются. Календарные сроки, исполнители и оценки трудоёмкости назначаются после уточнения объёма данных и декомпозиции.

Задачи M0 опубликованы 2026-11-19: [семь согласованных Issues](planning/m0-tickets-draft.md). Нативные блокирующие связи и метки проверены. Начать можно с [#1 — исходные данные](https://github.com/alkselsv/ActionFlow/issues/1) и [#2 — условия эксперимента](https://github.com/alkselsv/ActionFlow/issues/2). Ссылки ниже обозначают опубликованные задачи, а не их завершение; текущие статусы отслеживаются в GitHub.

2026-11-20: реальных клиентских чатов Vedita для эксперимента нет. #1 выполняется на согласованном синтетическом наборе [`data/fixtures/telegram/`](../data/fixtures/telegram/README.md) (9 чатов, 43 сообщения); состав, стороны и правила зафиксированы в [записи AF-001](experiment/af-001-source-data.md). Следствие: фактический формат Telegram export не проверяется, а качество на наборе остаётся предварительным.

## Границы и принципы планирования

- ActionFlow — самостоятельный продукт; ResponseFlow — первый модуль.
- Первый эксперимент: один менеджер, экспорт групповых чатов Telegram, один чат — один проект, только текст.
- Контекст, стороны участников и SLA проекта задаются вручную. Первая реакция отделена от решения обращения.
- Анализ запускается кнопкой. Три типа находок: `unanswered`, `commitment`, `complaint`. Закрытие подтверждает менеджер.
- PostgreSQL хранит предметные данные; Temporal исполняет процессы. Введение Celery или APScheduler для этих задач не планируется.
- Разметка и проверка качества начинаются до детекторов и сопровождают разработку. Сравнение моделей и Cognee не заменяет базовую проверку MVP.
- Cognee — экспериментальный вариант контекста. Его внедрение не блокирует готовность офлайн-MVP и может быть отложено по результатам проверки.
- Бот, документация, уведомления и внешние действия относятся к последующим этапам.

## Этапы и условия перехода

| Этап | Результат | Условие завершения |
| --- | --- | --- |
| M0. Подготовка | Образцы, правила, модель данных, технические решения | Входной формат проверен; открытые правила, влияющие на реализацию, разрешены или имеют явное поведение |
| M1. Офлайн-MVP | Импорт → кнопка анализа → очередь → решение менеджера | Пройдены функциональные критерии спецификации, сохранены базовые метрики и замечания менеджера |
| M2. Качество и контекст | Сравнение конфигураций и выбор для пилота | Определены пороги качества; на отложенных примерах проверена выбранная конфигурация; решение по Cognee записано |
| M3. Telegram-бот | Новые сообщения поступают в существующие проекты | Проверены доступ, сопоставление с экспортом, повторная доставка, восстановление и контроль полноты |
| M4. Проектная документация | Контекст и SLA из данных проекта | Условия имеют источники и версии; изменения не искажают исторические запуски |
| M5. Уведомления и действия | Уведомление → подтверждение → действие → проверка результата | Действия ограничены правами, повторное выполнение контролируется, результат проверяется |

M0 и M1 подробно описаны для подготовки тикетов. Работы M2–M5 — заготовки эпиков: перед реализацией они уточняются с учётом предыдущего этапа. M4 можно готовить параллельно M3 после проверки офлайн-MVP; полная поддержка документов не является обязательным условием подключения бота. Уведомления можно начать после M3, не ожидая завершения M4. Публикация и эксплуатация с реальными данными требуют технических решений AF-004.

**GitHub:** [#6 — предметная модель и состояния](https://github.com/alkselsv/ActionFlow/issues/6) → [#7 — контракты и исполнение анализа](https://github.com/alkselsv/ActionFlow/issues/7). #6 блокируется #5; #7 блокируется #6 и #4.

**Результат:** проверяемый проект модели данных, переходов состояний, контрактов и расположения модулей для первого эксперимента.

**Приёмка:**

- Описаны клиент, проект, чат, участник и его сторона, сообщение/наблюдаемая редакция, настройки/SLA, обращение, обязательство, кандидат, карточка ситуации, основания, запуск и решение менеджера.
- Разделены первая реакция, решение обращения, состояние обязательства и решение менеджера. Согласованы подтверждение, отклонение, откладывание, закрытие, обработка новых оснований после закрытия и защита решений от перезаписи анализом.

- Описаны HTTP-операции, структурированный результат детектора, границы транзакций и исполнения Temporal. Предложена структура репозитория под эти решения; прежние эскизы из PROTOTYPE.md сверены и заменены актуальными контрактами по мере их утверждения.

**GitHub:** [#2 — условия работы с данными и контур пилота](https://github.com/alkselsv/ActionFlow/issues/2) → [#4 — совместимость и стартовая конфигурация](https://github.com/alkselsv/ActionFlow/issues/4).

### AF-005. Поднять backend и прикладную БД

**GitHub:** [#8](https://github.com/alkselsv/ActionFlow/issues/8).

**Результат:** запускаемый FastAPI backend, PostgreSQL и миграции начальной модели.

**Приёмка:** чистое окружение поднимается по инструкции; миграции применяются; после перезапуска данные сохраняются. В конфигурации и Git отсутствуют секреты и реальные переписки; автоматические проверки проекта выполняются одной документированной командой.

### AF-006. Поднять веб-приложение и вход менеджера

**GitHub:** [#8](https://github.com/alkselsv/ActionFlow/issues/8).

**Результат:** React/TypeScript/Vite приложение с одной учётной записью менеджера.

**Приёмка:** менеджер входит и выходит; неавторизованный запрос к данным отклоняется backend; интерфейс отображает загрузку, пустой результат и ошибку. Дополнительные роли и управление несколькими пользователями не входят в работу.

### AF-007. Подключить Temporal и Python worker

**GitHub:** [#12](https://github.com/alkselsv/ActionFlow/issues/12).

**Результат:** окружение исполняет workflow и Activities вне HTTP-запроса.

**Приёмка:** локально доступны Temporal, worker и отдельные хранилища; контрольный процесс переживает перезапуск worker. Проверены ограниченные повторные попытки, таймауты, постоянная ошибка и наблюдаемость выполнения. Определён и проверен способ восстановления задания при сбое между записью приложения и стартом workflow; внешние вызовы остаются в Activities.

### AF-008. Реализовать ручные настройки проектов

**GitHub:** [#8](https://github.com/alkselsv/ActionFlow/issues/8), [#9](https://github.com/alkselsv/ActionFlow/issues/9).

**Результат:** менеджер задаёт клиента, проект, ответственного, стороны участников, контекст и SLA.

**Приёмка:** один чат привязывается к одному проекту; один клиент может иметь несколько проектов. Срок первой реакции, рабочий календарь и часовой пояс сохраняются с версией; неизвестная сторона участника отображается явно. Новые настройки не переписывают версии, использованные предыдущими запусками.

### AF-009. Импортировать текст Telegram JSON без дубликатов

**GitHub:** [#10](https://github.com/alkselsv/ActionFlow/issues/10), [#11](https://github.com/alkselsv/ActionFlow/issues/11).

**Результат:** экспорт превращается в сохранённые сообщения проекта с отчётом импорта.

**Приёмка:** проверены повторный импорт, несколько авторов, ответы, текст из составных полей, системные сообщения и повреждённый файл. Сохраняются внешние ID и доступные временные сведения; наблюдаемые изменения не уничтожают использованные ранее основания. Пропуски и необработанные вложения отражены в отчёте; неизвестные исторические редакции не выдумываются.

### AF-010. Показать импортированную переписку

**GitHub:** [#10](https://github.com/alkselsv/ActionFlow/issues/10), [#11](https://github.com/alkselsv/ActionFlow/issues/11).

**Результат:** менеджер проверяет импорт и исходные сообщения в браузере.

**Приёмка:** доступны автор, сторона участника, время, текст, связь ответа и отметка необработанного содержимого. Порядок сообщений устойчив; открытие конкретного сообщения показывает окружающую переписку. Чаты разных проектов не смешиваются.

### AF-011. Собирать входной срез и контекст анализа

**GitHub:** [#12](https://github.com/alkselsv/ActionFlow/issues/12), [#15](https://github.com/alkselsv/ActionFlow/issues/15).

**Результат:** воспроизводимый вход анализа с периодом, моментом оценки и версиями настроек.

**Приёмка:** поздние ответы, будущие переносы и новые настройки исключены из более раннего среза с учётом ограничений экспорта. Сохраняется состав входа; превышение допустимого объёма обрабатывается явно. Ранее возникшие незавершённые обязательства учитываются при повторном анализе; способ передачи истории не теряет их незаметно.

### AF-012. Реализовать LLM-вызов и проверку результата

**GitHub:** [#13](https://github.com/alkselsv/ActionFlow/issues/13).

**Результат:** заменяемый адаптер стартовой модели, структурированный результат и диагностика.

**Приёмка:** ответ проходит проверку схемы; ссылки на сообщения проверяются на существование и принадлежность разрешённому срезу/проекту. Проверены невалидный результат, лимит, таймаут и постоянная ошибка. Версии prompt/схемы/модели, параметры, потребление и доступная стоимость сохраняются; неизвестная стоимость не записывается как нулевая.

### AF-013. Находить обращения без содержательного ответа

**GitHub:** [#13](https://github.com/alkselsv/ActionFlow/issues/13).

**Результат:** кандидаты `unanswered` с основаниями и различением первой реакции и решения.

**Приёмка:** проверены вопрос без ответа, подтверждение получения без решения, содержательный ответ, ответ представителя клиента и обсуждение нескольких вопросов. Возможный ответ во вложении отражает неполноту данных. Основания и ожидаемые результаты сверены с разметкой; ошибки фиксируются для дальнейшего сравнения.

### AF-014. Извлекать и обновлять обязательства Vedita

**GitHub:** [#15](https://github.com/alkselsv/ActionFlow/issues/15).

**Результат:** кандидаты `commitment` и история содержания, исполнителя, сроков, отмены и исполнения.

**Приёмка:** проверены обещание, предположение, цитирование чужого обещания, перенос, отмена и сообщение об исполнении. Неустановленные исполнитель/срок остаются неизвестными по правилам AF-002. Новые основания связываются с исходным обязательством; повторный анализ сохраняет его историю.

### AF-015. Находить претензии клиента

**GitHub:** [#16](https://github.com/alkselsv/ActionFlow/issues/16).

**Результат:** кандидаты `complaint` с исходными сообщениями и объяснением.

**Приёмка:** на разметке различаются претензия, обычный вопрос, нейтральное обсуждение ошибки и цитата. Реакции сотрудников и клиента атрибутируются по настроенной стороне. Извлечённый вывод проверяется по тексту; ложные срабатывания включаются в отчёт качества.

### AF-016. Рассчитывать SLA и объяснимый приоритет

**GitHub:** [#14](https://github.com/alkselsv/ActionFlow/issues/14).

**Результат:** прикладные правила расчёта SLA первой реакции и приоритета по контракту кандидатов.

**Приёмка:** проверены границы рабочего дня, нерабочее время, календарь и часовой пояс на согласованных примерах. Первая реакция завершает соответствующий отсчёт без автоматического решения обращения. Результат ссылается на версию SLA и объясняет приоритет; при недостаточных данных расчёт не выдаётся за установленный факт. Тесты правил используют кандидатов согласованной схемы и не требуют готовности всех детекторов.

### AF-017. Сохранять ситуации и решения менеджера

**GitHub:** [#13](https://github.com/alkselsv/ActionFlow/issues/13), [#15](https://github.com/alkselsv/ActionFlow/issues/15), [#17](https://github.com/alkselsv/ActionFlow/issues/17).

**Результат:** карточки, основания, дедупликация и согласованные переходы состояний.

**Приёмка:** повторная находка не создаёт дубль; результаты разных запусков остаются доступны. Подтверждение, отклонение, откладывание и закрытие оставляют историю; система сама не закрывает ситуацию. Новый анализ не уничтожает решения; новые основания после закрытия обрабатываются по AF-003. Обязательство и карточка имеют раздельное состояние.

### AF-018. Собрать запуск анализа по кнопке

**GitHub:** [#12](https://github.com/alkselsv/ActionFlow/issues/12), [#13](https://github.com/alkselsv/ActionFlow/issues/13), [#18](https://github.com/alkselsv/ActionFlow/issues/18).

**Результат:** импортированный чат проходит полный анализ через Temporal с сохранением результата.

**Приёмка:** HTTP-запрос возвращает идентификатор запуска; доступны ожидание, выполнение, успех и ошибка. Повторная доставка команды и повтор Activities не создают дубликаты; намеренный новый запуск получает отдельный результат. Проверены перезапуск worker, ошибка провайдера и восстановление после частичного сохранения. Выбранный исторический срез сохраняется на всём протяжении запуска.

### AF-019. Реализовать очередь, карточку и действия менеджера

**GitHub:** [#13](https://github.com/alkselsv/ActionFlow/issues/13), [#14](https://github.com/alkselsv/ActionFlow/issues/14), [#17](https://github.com/alkselsv/ActionFlow/issues/17).

**Результат:** менеджер рассматривает ситуации и принимает решения в веб-интерфейсе.

**Приёмка:** работают фильтры по проекту, типу, приоритету и статусу, счётчики открытых ситуаций и нарушений SLA. Карточка показывает описание, приоритет и его объяснение, SLA, рекомендацию, основания с окружающими сообщениями и историю. Четыре действия сохраняются; устаревшее состояние карточки обрабатывается без потери решения. Интеграционная проверка выполняется с реальными результатами AF-018.

### AF-020. Сравнивать запуски и измерять базовое качество

**GitHub:** [#18](https://github.com/alkselsv/ActionFlow/issues/18).

**Результат:** повторный анализ исторического набора и отчёт сравнения.

**Приёмка:** доступны метрики по трём типам, корректность оснований, дубли, ошибки SLA, длительность и стоимость. Определены правила сопоставления находок с разметкой; результаты сопоставимы при одинаковом входном срезе. Сравнение не перезаписывает решения менеджера; ошибки сохраняются для разбора. Инструмент оценки детекторов отделён от replay Temporal.

### AF-021. Подготовить эксплуатацию первого эксперимента

**GitHub:** [#19](https://github.com/alkselsv/ActionFlow/issues/19).

**Результат:** выбранный контур пригоден для работы менеджера и сохранения данных.

**Приёмка:** проверены доступ по выбранной схеме, резервное копирование и восстановление БД; перезапуск компонентов не теряет сохранённые решения. По идентификатору запуска можно найти состояние и ошибку, логи не раскрывают переписку без необходимости. Документированы запуск, конфигурация, диагностика и удаление экспериментальных данных; подтверждено выполнение условий AF-004.

### AF-022. Провести приёмку офлайн-MVP с менеджером

**GitHub:** [#20](https://github.com/alkselsv/ActionFlow/issues/20).

**Результат:** протокол первого эксперимента: функциональная приёмка, базовые метрики и обратная связь.

**Приёмка:** все восемь критериев из спецификации проверены на сохранённом наборе. Менеджер прошёл импорт, настройки, запуск, просмотр оснований и четыре действия; повторный запуск сохранил историю. Известные ошибки и ограничения записаны, результаты не объявляются готовностью к живому пилоту без оценки M2.

## M2. Проверка качества и выбор контекста

Работы этого и следующих разделов уточняются до создания исполнимых тикетов. Условия принятия решений определяются до сравнения на отложенных примерах; даты и числовые пороги пока не назначены.

### AF-023. Сравнить модели, prompts и правила

**Зависимости:** AF-020, AF-022.

**Результат и приёмка:** на одном входном наборе сопоставлены качество по типам, корректность оснований, ошибки SLA, стоимость и время. Изменения настраиваются на выделенных примерах; выбранный вариант проверен на отложенной части. Записаны ограничения и рекомендуемая конфигурация.

### AF-024. Проверить Cognee на переписках

**Зависимости:** AF-011, AF-020; может выполняться параллельно AF-023 после готовности входов и оценки.

**Результат и приёмка:** одинаковые детектор и модель сравниваются с базовым контекстом и контекстом Cognee. Проверены обсуждение целиком, авторство, источники, перенос/отмена обещания, редакции, удаление, разделение проектов и исторический срез. Измерены стоимость индексации и поиска, задержка и прирост качества. Записано решение: применять, доработать или отложить; документального наличия функции недостаточно для положительного решения. Материалы: [обзор](research/cognee-memory.md), [примеры чатов](research/cognee-chat-examples.md).

### AF-025. Согласовать готовность к живому пилоту

**Зависимости:** AF-022, AF-023; AF-024 обязателен, если Cognee входит в выбранную конфигурацию.

**Результат и приёмка:** с менеджером согласованы допустимый шум, полнота обнаружения, корректность оснований и SLA, стоимость и задержка. Выбранная конфигурация проверена на отложенных данных; ограничения и критерии остановки пилота записаны. Cognee имеет явный статус, включая допустимое решение отложить его. При непрохождении порогов определены исправления и повторная проверка.

## M3. Подключение Telegram-бота

### AF-026. Проверить доступ бота и сопоставление с экспортом

**Зависимости:** AF-001, AF-004. Техническую проверку можно подготовить до завершения M2 на разрешённом тестовом чате.

**Результат и приёмка:** в одном групповом чате проверены права, состав доступных событий, ID, новые сообщения и доступные изменения. Зафиксированы ограничения истории/удалений, возможность пропуска и порядок подключения существующего проекта. Чтение и отправка разведены по разрешениям; эксперимент не отправляет клиентам сообщения от имени менеджера.

### AF-027. Реализовать приём и сверку новых сообщений

**Зависимости:** AF-009, AF-017, AF-026.

**Результат и приёмка:** события бота поступают в ту же предметную модель, что экспорт. Проверены пересечение с импортом, повторная и нарушенная по порядку доставка, доступные правки и восстановление в пределах возможностей источника. Потеря доступа и потенциальный пропуск данных видимы; отсутствие данных не трактуется как отсутствие ответа.

### AF-028. Запускать анализ по событиям и контролировать сроки

**Зависимости:** AF-007, AF-018, AF-027.

**Результат и приёмка:** новые сообщения инициируют анализ; Temporal Schedules выполняет согласованные сверки, workflow учитывают сроки, переносы и события исполнения. Определены и проверены правила конкурирующих запусков, частоты анализа и повторной доставки. После рестарта ожидающие процессы продолжаются; настройки частоты и рабочего времени согласованы до включения.

### AF-029. Провести ограниченный живой пилот

**Зависимости:** AF-021, AF-025, AF-027, AF-028.

**Результат и приёмка:** выбраны проекты и период наблюдения; менеджер регулярно работает с очередью. Измерены полнота приёма, задержка обнаружения, шум и полезность. Проверены восстановление после сбоя и остановка обработки; выводы сопоставлены с критериями AF-025. Расширение охвата выполняется после разбора результата.

## M4. Контекст и SLA из проекта

### AF-030. Подключить проектные документы с версиями

**Зависимости:** AF-008, AF-011, AF-022.

**Результат и приёмка:** выбраны источник и поддерживаемые форматы; документы привязаны к проекту, имеют версии и адресуемые фрагменты-основания. Изменение или удаление документа отражается в поиске; контекст другого проекта не попадает в анализ. Типы документов и ограничения объёма уточняются перед реализацией.

### AF-031. Получать SLA и условия из проектных данных

**Зависимости:** AF-002, AF-008, AF-016, AF-030.

**Результат и приёмка:** определены источник условий, связь с типом клиента, приоритет источников и правила применения изменений. Отсутствующий/противоречивый SLA виден менеджеру; каждое применённое условие имеет основание и версию. Исторические запуски используют прежние условия. Порядок подтверждения извлечённых настроек согласуется до их автоматического применения.

### AF-032. Проверить пользу проектного контекста

**Зависимости:** AF-020, AF-030, AF-031; AF-024 при использовании Cognee.

**Результат и приёмка:** сравнение с ручным контекстом показывает влияние документов на качество, основания, стоимость и задержку. Проверены конфликт текста переписки с документом, обновление условий и устаревший источник. Решение о включении фиксируется по измерениям.

## M5. Уведомления и контролируемые действия

### AF-033. Добавить уведомления менеджеру

**Зависимости:** AF-019, AF-029.

**Результат и приёмка:** выбран первый канал Telegram или Битрикс24; уведомление ведёт к ситуации и её основаниям. Настроены получатель, периодичность, рабочее время и защита от повторов. Рестарт и повторная доставка не создают поток одинаковых уведомлений; при смене приоритета действует согласованная политика.

### AF-034. Подготовить действие и получить подтверждение

**Зависимости:** AF-017, AF-019, AF-029.

**Результат и приёмка:** выбран один вид действия, например создание задачи Битрикс24. Менеджер видит точный объект, параметры, основания и может изменить, подтвердить или отклонить предложение. Подтверждение относится к конкретной версии действия; устаревшее предложение проходит повторную проверку. Прямые автоматические сообщения клиенту остаются отдельным будущим решением.

### AF-035. Выполнить действие Битрикс24 и проверить результат

**Зависимости:** AF-007, AF-034; доступ к тестовому контуру Битрикс24.

**Результат и приёмка:** подтверждённое действие проверяет разрешения, создаёт или связывает задачу, сохраняет внешний ID и аудит. Повтор Activities и потеря ответа не создают неконтролируемые дубли; неоднозначный результат требует сверки. Состояние внешней задачи сверяется с источником и служит основанием для предложения закрытия; окончательное закрытие ситуации остаётся решением менеджера.

## Как создавать тикеты по этому плану

Для M0–M1 используется отдельный тикет на каждый AF-ID либо несколько дочерних тикетов, если работа не помещается в один проверяемый результат. AF-ID сохраняется в заголовке/теле; после публикации здесь добавляется ссылка на фактический GitHub Issue. Номера задач не угадываются заранее.

Тикет содержит:

- проблему и результат для пользователя или разработчика;
- ссылку на AF-ID и соответствующие требования спецификации;
- входы, выходы, включённый объём и явные исключения;
- зависимости по фактическим GitHub Issues;
- критерии приёмки из плана и способ содержательной проверки;
- открытые решения, требующие ответа до реализации, и необходимые данные/доступы.

Работы с открытыми правилами не получают готовность к автономной реализации, пока правила не разрешены. Задачи M2–M5 сначала уточняются до такого же уровня. Статусы и метки назначаются по [правилам трекера](agents/issue-tracker.md) и [словарю меток](agents/triage-labels.md).

## Начальный порядок и зависимости

1. M0 начинается с #1 (исходные данные — выполнен на синтетическом наборе) и #2 (условия эксперимента). Цепочки: #1 → #3 → #5 → #6 → #7 и #2 → #4 → #7. #3 работает с синтетическими примерами; фактический формат реального экспорта на этом этапе не проверяется.
2. После завершения M0 #7 начинается [#8](https://github.com/alkselsv/ActionFlow/issues/8); далее — настройки, импорт, подготовка среза и первый детектор по таблице M1.
3. После [#13](https://github.com/alkselsv/ActionFlow/issues/13) работа над решениями менеджера может идти параллельно SLA и новым детекторам. После SLA обязательства и претензии развиваются независимо.
4. [#18](https://github.com/alkselsv/ActionFlow/issues/18) объединяет три типа и проверяет сравнение запусков; [#19](https://github.com/alkselsv/ActionFlow/issues/19) готовит эксплуатацию. После обеих работ выполняется приёмка [#20](https://github.com/alkselsv/ActionFlow/issues/20).

Зависимость обозначает необходимый завершённый результат. Параллельная подготовка возможна при согласованных контрактах и независимом владении изменяемыми файлами. Все фактические блокировки M0/M1 заданы нативными связями GitHub.

## Связь с критериями спецификации MVP

| Критерий спецификации | Основные работы |
| --- | --- |
| 1. Импорт, отображение и отсутствие дублей сообщений | AF-009, AF-010 |
| 2. Ручные проект, стороны участников, контекст и SLA | AF-008 |
| 3. Запуск по кнопке, результат и ошибки | AF-007, AF-012, AF-018 |
| 4. Три типа находок и проверяемые основания | AF-012–AF-015, AF-017, AF-019 |

AF-021 проверяет эксплуатационную готовность, AF-022 — весь пользовательский цикл. Полезность и пороги для следующего этапа проверяются в M2. Выход за согласованный MVP — MAX, голосовые, дополнительные пользователи, автоматическая отправка клиенту и другие модули — требует отдельного решения о расширении объёма.
