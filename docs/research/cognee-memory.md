# Cognee как память для мониторинга клиентских коммуникаций

Дата проверки: 2026-11-19. Исследование официальной документации и репозитория; без запуска продукта. Это материал для обсуждения, не ADR и не решение о внедрении.

## Вывод для обсуждения

Cognee стоит проверить как восстанавливаемую проекцию контекста: поиск связанных сообщений, участников, обещаний и объяснений со ссылками на источники. Канонические сообщения, их редакции, права и состояния обязательств разумно оставить в прикладной БД. Это наша инженерная гипотеза: перечисленные ниже функции Cognee помогают искать контекст, но документация не доказывает полноту извлечения обязательств, корректность дедлайнов или транзакционную согласованность с внешними системами.

## Что подтверждено источниками

| Область | Подтвержденная возможность и ограничение |
| --- | --- |
| Загрузка | `remember()` принимает текст, файлы, URL и `DataItem` с `data_id`, label и external metadata; строит chunks, граф и embeddings. Session mode хранит короткую память отдельно и переносит ее в граф через improve. Permanent ingestion тяжелее session write; при фоновой индексации поиск может видеть частичные результаты. [Remember](https://docs.cognee.ai/core-concepts/main-operations/remember) |
| Коммуникации и обновления | Есть Gmail connector через dlt: первый импорт, инкрементальные изменения, forget-on-delete при следующей синхронизации. В примере используются `primary_key=id`, `merge` и полный охват корпуса при очистке. Это подтверждает конкретный connector, а не универсальный CDC для любого мессенджера. [Gmail ingestion](https://docs.cognee.ai/guides/gmail-ingestion) |
| Поиск | Relational store хранит метаданные и происхождение, vector store — embeddings, graph store — сущности и связи. [Architecture](https://docs.cognee.ai/core-concepts/architecture). Hybrid retrieval соединяет passages, entities и facts; `only_context=True` позволяет получить контекст до генерации ответа, параметры регулируют вклад частей. [Hybrid retrieval](https://docs.cognee.ai/guides/hybrid-retrieval-recall) |
| Время | Даты текста извлекаются в Timestamp nodes с точностью и интервалом. TEMPORAL извлекает окно вопроса через LLM, собирает hybrid candidates и повышает позиции связанных с окном результатов. При нераспознанном окне или отсутствии датированных попаданий возвращается обычный hybrid search. Это **не доказательство строгого исторического as-of запроса**. [Temporal graph](https://docs.cognee.ai/guides/temporal-knowledge-graph) |
| Конфликты | Improve может передавать LLM потенциально противоречивые факты разных документов и создавать FactConflict. Использует `effective_date` источника, требует LLM, edge evidence и совместимого graph adapter. В текущих docs включен по умолчанию; до 1.6.5 включительно был выключен. Автоматическое определение противоречий остается модельным суждением. [Review conflicts](https://docs.cognee.ai/guides/review-conflicts) |
| Происхождение | Есть проекция Tenant → User → Agent → Dataset → file и связи извлеченной памяти с файлами. У функции provenance без scope глобальная видимость; tenant scope сам по себе также показывает datasets без пользовательского grant. Нужен дополнительный scope по readable dataset IDs. Это интерфейс, который нельзя напрямую выдавать клиенту без проверки прав. [Memory provenance](https://docs.cognee.ai/guides/memory-provenance) |
| Мультитенантность | Граница изоляции — dataset, с отдельным graph/vector backend и read/write/share/delete permissions для users, roles, tenants. Tenant — группа прав, а не отдельная БД. Поддержка зависит от выбранных backend handlers. **В single-user mode фильтры datasets/dataset_ids при поиске игнорируются**, поэтому одним именованием datasets клиентов изолировать нельзя. [Isolation](https://docs.cognee.ai/core-concepts/multi-user-mode/data-isolation-and-multi-tenancy) |
| Удаление | `forget()` удаляет document/dataset и производные graph/vector/relational данные, очищает связанные session answers. Но удаление одного документа оставляет search history; для собственных записей нужен `clean_history=True`. `forget(everything=True)` не равен уничтожению raw uploaded files. Нужно проверять весь жизненный цикл хранения, включая внешние архивы. [Forget](https://docs.cognee.ai/core-concepts/main-operations/forget) |
| Развертывание | Python SDK, HTTP API, Docker и managed Cloud. README описывает локальные модели без API key и optional LLM providers; production GLiNER extraction и production Postgres graph отдельно оговорены как коммерческие предложения, Postgres graph OSS — demo. Базовый репозиторий имеет Apache-2.0. [README](https://github.com/topoteretes/cognee/), [LICENSE](https://github.com/topoteretes/cognee/blob/main/LICENSE) |

Зависимости эксплуатации: relational, vector и graph store плюс session cache; они могут быть локальными или внешними. Локальные SQLite/LanceDB/Ladybug файлы нельзя разделять между процессами; docs рекомендуют внешний Postgres/PGVector и Neo4j за одним Cognee service для общего доступа. Поэтому масштабирование SaaS нужно проверить отдельно от локального quickstart. [Remember: concurrent recall](https://docs.cognee.ai/core-concepts/main-operations/remember)

## Что должен проверить короткий spike

1. **Извлечение на нашем корпусе:** русский/смешанный язык, обещание vs предположение, отмена/перенос, цитаты чужих сообщений, несколько участников с одинаковыми именами. Сравнить полноту и точность с простым retrieval по chunks; наличие графа само по себе не доказывает прирост.
2. **Историческая корректность:** воспроизводить корпус в состоянии на момент оценки; сообщение о переносе завтра не должно влиять на вчерашнее решение. Отдельно хранить время события, время получения и редакцию источника; проверить, что temporal retrieval не подмешивает поздние факты.
3. **Доказательства:** каждый вывод об обязательстве должен возвращать message ID, revision, цитату/диапазон и время источника. File-level provenance недостаточно, чтобы автоматически считать эту детализацию обеспеченной.
4. **Права:** два клиента с одинаковыми сущностями, private/shared channels, отзыв доступа и переезд сообщения; проверить retrieval, sessions, provenance, history, graph inspection и кеш. Dataset ACL не доказывает автоматический перенос динамических ACL исходного мессенджера.
5. **Обновления/удаление:** повторный webhook, измененный текст с тем же ID, удаленное единственное доказательство, факт с двумя независимыми источниками, сбой между записями в stores; проверить отсутствие старых ответов, повторяемость и восстановление проекции.
6. **Эксплуатация:** зафиксировать release и комбинацию adapters; измерить цену и задержку ingestion/improve/recall, рост числа datasets, конкурирующие записи, резервное копирование и восстановление. Документация API и SDK меняется: не переносить параметры между версиями без проверки установленной схемы.

Условия результата spike: полезность измеряется обнаружением реальных обязательств с проверяемыми источниками и контролем ложных срабатываний; приемлемость для SaaS — отсутствием межклиентских утечек и корректным отзывом/удалением. До этого Cognee остается кандидатом на индекс контекста.
