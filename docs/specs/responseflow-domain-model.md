# ResponseFlow — предметная модель и состояния

AF-003, часть 1, [#6](https://github.com/alkselsv/ActionFlow/issues/6). Модель опирается на [спецификацию MVP](responseflow-mvp.md), [формат импорта AF-001](../experiment/af-001-import-format.md) и [утверждённые правила AF-002](../experiment/af-002-annotation.md). Контракты и границы исполнения описываются отдельно в #7.

## Сущности и связи

| Сущность | Ответственность и связи |
| --- | --- |
| Клиент и проект | У клиента один или несколько проектов. Проект принадлежит одному клиенту и имеет ответственного менеджера. |
| Чат и участник | Чат привязан к одному проекту. Участник определяется устойчивым идентификатором автора в источнике. Принадлежность Vedita, клиенту или неизвестной стороне задаётся в настройках проекта. Системная запись имеет отдельный тип. |
| Сообщение и наблюдаемая редакция | Сообщение принадлежит чату, хранит автора, исходное время и связь ответа. Редакция фиксирует наблюдённое содержимое, время наблюдения и доступные сведения об изменении. |
| Версии настроек | На проекте хранятся неизменяемые версии контекста, сторон участников и SLA вместе с календарём и часовым поясом. Изменение создаёт новую версию. |
| Обращение | Якорь — исходный запрос или сообщение о блокирующем сбое. Хранит отдельные события первой реакции и решения с основаниями и временем. Повторы запроса связываются с обращением. |
| Обязательство | Якорь — исходное обещание и обязательство, выделенное в нём. Хранит предмет, исполнителя при наличии и события назначения срока, переноса, исполнения и отмены. Может относиться к обращению. |
| Кандидат на карточку ситуации | Результат конкретного запуска с типом, якорем, описанием, оценкой уверенности, предложенным действием и основаниями. Несколько запусков могут дать кандидатов на одну карточку. |
| Карточка ситуации | Устойчивое представление одного предмета одного типа в очереди проекта. Хранит историю наблюдений, предложений и решений менеджера. |
| Основания | В MVP основание из переписки ссылается на конкретную редакцию и при необходимости на фрагмент текста. Основания связываются с кандидатами, предметными событиями и решениями менеджера. Если менеджер подтверждает разрешение вне переписки, решение хранит его объяснение отдельно от сообщений-оснований. |
| Запуск | Проект, диапазон и момент оценки, снимок входа, версии настроек и анализа, кандидаты, ошибки, длительность и доступные данные о стоимости. |
| Решение менеджера | Неизменяемая запись с действием, автором, временем, комментарием, предыдущим и новым статусом. Указывает, какие основания и предложение видел менеджер. |

## Идентичность и исторический срез

- Чат определяется парой «источник, внешний ID чата» внутри рабочей области. Сообщение определяется парой «чат, внешний ID сообщения». В синтетическом наборе используется исходный `external_id`, в Telegram-style экспорте без такого поля — локальный ID сообщения внутри чата.
- Повторный импорт совпадающего сообщения обновляет сведения о последнем наблюдении и не создаёт редакцию. Наблюдаемое изменение анализируемых полей создаёт редакцию с новым номером. Если более позднее изменение возвращает прежний текст, это новая редакция. Повтор старой выгрузки с известным более ранним временем источника не заменяет известную актуальную редакцию. При конфликте без надёжного порядка сохраняются наблюдения и пометка неопределённости. Отсутствие записи в экспорте не доказывает удаление.
- Первая видимость редакции неизменяема. В текущей очереди это первое наблюдение системой. Для ретроспективной оценки допустимо явно заявленное время наблюдения источника, как в синтетическом наборе AF-002. Физическое время импорта хранится отдельно. Если историческую видимость подтвердить нельзя, ретроспективный срез помечается неполным; время отправки не подставляется вместо времени наблюдения. Для оценки на момент T используются сообщения с временем отправки не позже T и редакции, наблюдённые не позже T. Если две версии нельзя однозначно упорядочить по доступным сведениям, случай помечается как неопределённый. Снимок запуска фиксирует точные редакции и версии настроек. Историческое сравнение использует настройки, доступные на T. Эксперимент с другой версией настроек помечается отдельно и сохраняет явную версию.
- Якорь обращения, обязательства или претензии содержит внутренний ID исходного сообщения и устойчивое различение предметов одного типа внутри этого сообщения. При первом появлении приложение назначает предмету ID и сохраняет привязку к фрагменту редакции. Повторное наблюдение сопоставляется с сохранённым предметом по ссылкам на сообщения и смыслу. Перефразирование, изменение срока или позиции фрагмента не меняют ID. При неоднозначном сопоставлении кандидат сохраняется для ручной проверки без автоматического создания дубля. Поздний импорт более раннего основания добавляет связь с существующим предметом.
- Ключ карточки — `(project_id, finding_type, subject_id)`, где subject соответствует обращению для `unanswered`, обязательству для `commitment` или эпизоду претензии для `complaint`. Одно сообщение может дать несколько предметов. Приложение обеспечивает уникальность ключа даже при повторных или параллельных запусках. Повторные жалобы по тому же незавершённому эпизоду дополняют основания. Самостоятельная претензия по новому эпизоду получает отдельный ID.
- Кандидаты и основания каждого запуска сохраняются независимо. Повторная доставка результата того же запуска не изменяет историю. Исторический запуск применяется только для сравнения и не обновляет текущую очередь. Для текущих запусков результат с более ранним срезом сохраняется в истории без замены более свежего наблюдения.

## Предметные состояния

**Обращение.** С первого запроса оно открыто. Первая подтверждённая реакция Vedita останавливает SLA по [AF-002](../experiment/af-002-annotation.md). Содержательный ответ может одновременно быть реакцией и решением. Подтверждение получения оставляет обращение открытым. Для неполных данных признаки реакции и решения помечаются как неопределённые, пока проверяющий не установит их по основаниям. Просрочка первой реакции вычисляется по версии календаря и остаётся в истории после ответа. Норматив решения обращения для MVP не задан.

**Обязательство.** После обещания оно открыто. Свойства «срок отсутствует» и «просрочено» вычисляются на момент оценки. Перенос сохраняет предыдущий срок и основание. Явное исполнение или отмена завершают предметное обязательство и дают основание предложить закрытие карточки. Редакция или исчезновение фразы в выгрузке не равны отмене. Неоднозначный перенос или исполнение требуют ручной проверки.

## Карточка и действия менеджера

Начальный статус — «новая». Открытые статусы — «новая», «подтверждена», «отложена». Отсрочка хранит время следующего показа. Напоминание возвращает карточку в очередь с отметкой об истёкшей отсрочке, сохраняя статус и предыдущее решение.

| Действие | Из какого статуса | Результат |
| --- | --- | --- |
| Подтвердить | новая, отложена; отклонена при принятии предложения о пересмотре; закрыта при принятии предложения о переоткрытии | подтверждена; возврат отклонённой или закрытой карточки фиксирует новый эпизод рассмотрения той же карточки |
| Отклонить | новая, подтверждена, отложена | отклонена, с причиной |
| Отложить | новая, подтверждена, отложена | отложена до указанного времени |
| Закрыть | новая, подтверждена, отложена | закрыта, с основанием разрешения |

Анализ обновляет наблюдение и может предложить действие, сохраняя последнее решение менеджера. Новыми существенными основаниями считаются изменённый смысл, новый срок, исполнение, явная отмена или новая эскалация по тому же предмету. Повтор того же вывода, пересчёт уверенности и исчезновение кандидата сами по себе не меняют статус. Отказ от предложения записывается в историю предложения и сохраняет статус карточки. Повторный анализ тех же оснований не создаёт заново отклонённое предложение.

- Для отклонённой карточки существенное основание может дать предложение пересмотреть решение. Для закрытой — предложение переоткрыть её, если основание показывает продолжение того же предмета. До принятия предложения прежний статус сохраняется. Менеджер может его отклонить с сохранением истории.
- Для отложенной карточки новое основание сохраняется сразу. Существенное изменение показывается менеджеру как предложение вернуться к рассмотрению раньше, а обычное обновление сохраняет срок отсрочки. Подтверждение возврата переводит карточку в статус «подтверждена» и снимает текущую отсрочку. Менеджер также может отложить карточку до нового срока.
- Решение применяется к той версии карточки и предложения, которые видел менеджер. Если между просмотром и действием они изменились, нужно показать обновлённые основания перед применением. Повторная отправка того же действия не добавляет вторую запись.

## Проверка на сценариях

Вариация n-004 с переносом срока принята 2026-11-21 как контрольный сценарий для #6. Она дополняет сценарии проверки модели и не изменяет утверждённую разметку AF-002.

| Сценарий | Результат проверки модели |
| --- | --- |
| AF-002, n-001, №2 → №3 → №5 → №6 → №10 → №12 | №3 фиксирует первую реакцию и обещание дать пояснение, №5 решает обращение и подтверждает исполнение первого обещания. №6 даёт отдельное обязательство по смете до 15 сентября 09:00 UTC. №10 сообщает, что смета не получена, а №12 открывает обращение по сроку. На срезе 10:35 UTC есть просроченное обязательство и нарушение SLA по №12; №13 станет доступно позднее. |
| AF-002, n-004, №1 → №2 → №3 → №4, с проектной вариацией | На исходном срезе №2 фиксирует реакцию и обещание, №3 сообщает об исполнении, №4 подтверждает получение. В отдельной мысленной вариации ранний запуск после №2 создаёт карточку открытого обязательства. Между этим запуском и №3 стороны явно согласуют перенос срока с 09:10 на 10:00 UTC. Это та же карточка с двумя записями срока. №3 и №4 дают предложение закрыть, менеджер закрывает. Повторный анализ сохраняет решение. При новой явной эскалации по этому обязательству возникает предложение переоткрыть ту же карточку. Если вместо исполнения пришла явная отмена, сохраняется событие отмены с отдельным основанием. Вариация проверяет переходы и не меняет утверждённую разметку AF-002. |
| AF-002, n-007, №1–4 | Сбой обмена заказами считается обращением, №2 является реакцией и содержит обещание без срока, №3 повышает приоритет из-за риска остановки работ. Обращение, обещание Vedita и претензия с основанием №3 дают три карточки высокого приоритета с разными ключами. Замечание без блокирующего сбоя проверяется отдельно в n-008. |
| AF-002, n-007, №1–2 → №3, с проектной вариацией | Если менеджер отклонил карточку по сообщению о сбое, повтор №1–2 сохраняет отклонение. Явная эскалация в №3 даёт предложение пересмотреть решение о том же сбое. Если карточка была отложена, №3 даёт предложение вернуться раньше, сохраняя решение об отсрочке. |
| AF-001, `edge-reimport-s-006-first.json` → `edge-reimport-s-006-second.json` | Повторные записи сопоставляются по внешним ID. Изменившаяся запись получает новую редакцию, вновь появившаяся — новый ID. Старый запуск и решение по нему по-прежнему ссылаются на старый текст. Новый анализ может предложить изменение, если новая редакция меняет вывод. Повторный импорт второго файла не создаёт дублей. |
