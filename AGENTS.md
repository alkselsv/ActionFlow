# Инструкции для работы с ActionFlow

ActionFlow — самостоятельный продукт для преобразования клиентских коммуникаций в контролируемые действия. ResponseFlow — его первый модуль для Vedita.

## Документы и область работ

Перед проектированием или реализацией прочитай спецификацию MVP, относящиеся к задаче пункты дорожной карты и разделы архитектуры:

| Документ | Когда читать и что он определяет |
| --- | --- |
| [Спецификация MVP](docs/specs/responseflow-mvp.md) | Требования, границы первого эксперимента, сценарии менеджера и критерии готовности |
| [Дорожная карта](docs/ROADMAP.md) | Выбор и декомпозиция задач, AF-ID, зависимости, результаты и критерии приёмки |
| [Прототип](PROTOTYPE.md) | Архитектура, рабочий стек и распределение ответственности |
| [README](README.md) | Позиционирование и долгосрочные направления развития продукта |

Для текущего MVP руководствуйся спецификацией. Будущие возможности из README и исследовательских заметок включаются в работу только в рамках выбранной задачи и согласованного объёма. Решения, отмеченные как открытые или экспериментальные, сохраняют этот статус до их проверки или согласования.

При изменении требования обнови спецификацию, затем затронутые пункты дорожной карты и связанные тикеты. Архитектурные изменения также отражай в PROTOTYPE.md. Если документы расходятся, используй последнее явное решение пользователя и устрани расхождение до зависимой реализации.

## Работа по дорожной карте и тикетам

- При работе над тикетом прочитай его условия и связанный AF-ID, проверь результаты зависимостей и критерии приёмки. Планирование зависимости само по себе не означает её выполнение.
- При создании тикетов следуй разделу «Как создавать тикеты по этому плану» в docs/ROADMAP.md. AF-ID обозначает работу в плане; после публикации добавь к нему ссылку на фактический GitHub Issue.
- M0–M1 содержат подробные заготовки задач; M2–M5 уточняются перед реализацией. Вопросы, влияющие на поведение или контракт, разрешай до выполнения зависимой части работы.
- Готовность подтверждай критериями приёмки и содержательной проверкой. Команды запуска и проверок определяй по актуальным файлам проекта; одни изменения документации не подтверждают работоспособность приложения.

## Данные эксперимента

Используй обезличенные или синтетические примеры в репозитории. Реальные клиентские переписки, документы, секреты и учётные данные храни вне Git. Сохраняй связь результатов анализа с источниками и версиями, а также историю решений менеджера согласно спецификации.

## Agent skills

### Выбор процесса

При выборе скилла или объяснении порядка его использования прочитай [краткую инструкцию](docs/agents/matt-pocock-skills.md). Поведение конкретного скилла определяет его установленный SKILL.md.

### Issue tracker

Задачи отслеживаются в GitHub Issues репозитория alkselsv/ActionFlow.
Перед операциями с трекером прочитай [docs/agents/issue-tracker.md](docs/agents/issue-tracker.md).

### Triage labels

Перед разбором задач прочитай [docs/agents/triage-labels.md](docs/agents/triage-labels.md): он задаёт соответствие пяти ролей triage меткам трекера.

### Domain docs

Перед изучением предметной области прочитай [docs/agents/domain.md](docs/agents/domain.md), затем GLOSSARY.md и относящиеся к задаче ADR по указанным там правилам. Термины и зафиксированные решения используй при проектировании, реализации и оценке изменений.
